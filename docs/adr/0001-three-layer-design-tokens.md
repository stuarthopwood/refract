# Three-layer design tokens: palette, semantic roles, component tokens

Refract's colours currently live mostly as semantic-role custom properties (`--background`, `--card`, `--accent`, and the like) referenced directly by components, with hex literals and Tailwind palette/opacity classes still appearing ad hoc. The #474 design grill (agenda item 9 / B4, #456, #458) decided on a strict three-layer model instead: palette (raw values, never referenced directly), semantic roles (`background`, `surface-1` to `surface-3`, `border`, `accent`, `state-*`, `severity-*`), and component tokens per element (for example `--chat-user-bubble-bg`) that default to a semantic role. Components may use only layers 2 and 3; no hex literals, no Tailwind palette colours, no opacity modifiers, to be enforced by a lint script beside `check:ui-text`. `pnpm check:literal-colours` (#1473, spec 083) now enforces the hex and palette-class rules with a shrink-only baseline; opacity modifiers are enforced by `check:alpha-modifiers`.

This is hard to reverse once component tokens are threaded through markdown, chat bubbles, and the composer (#456 is the working default group under it; no build order was decided), surprising to a reader used to the current two-layer pattern, and a real trade-off: a flatter two-layer model (palette plus semantic roles only, no component tokens) would have been simpler but would force every themeable element to share a role's colour even when one element needs its own override (the "hot-pink-bubble" custom-theme case); keeping the current ad hoc mix of tokens, hex, and Tailwind utilities was rejected outright because it is what made theme files (#458) and the contrast script unenforceable in the first place.
