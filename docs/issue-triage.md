# Issue triage automation

The **Issue triage** workflow (`.github/workflows/issue-triage.yml`) classifies every new GitHub issue and, for spec-worthy issues, prepares Spec Kit artifacts as a draft pull request. It lives outside the Pinion app.

## What it does

**Stage 1: triage** (job `triage`) runs on `issues: opened` and on manual dispatch.

1. Reads the issue and the list of open issues.
2. Classifies it: type, area, priority (`p1` to `p3`), state, possible duplicate, and Spec Kit route.
3. Adds the missing labels, plus `triaged`, and posts one comment that starts with `> *This was generated by AI during triage.*`.

Rules:

- Labels a maintainer already set (type, area, priority) always win. Only missing dimensions are filled.
- The bot records which labels *it* applied in a hidden JSON marker inside its own comment (`<!-- pinion-issue-triage {"labels":[...]} -->`). A `force` re-triage uses that marker to tell its own earlier guesses apart from a maintainer's — it never treats its own previous output as a pin a human set, but a label a maintainer actually added is still never overridden.
- Every classification dimension (type, area, priority, state) is mutually exclusive: a re-triage removes any other bot-owned label from that dimension that the new result disagrees with — not only a stale state label — while leaving any maintainer-set label alone even if this run would have chosen differently.
- An issue with the `triaged` label is skipped unless you dispatch with `force`.
- Possible duplicates get a comment and the `needs-triage` state. Nothing is closed automatically.
- The model's rationale is always rendered as a single inline code span in the comment, so an untrusted `#123` reference, `[link](url)`, `![image](url)`, or stray backtick in it can never auto-link, render, or break the comment.

| Priority | Meaning |
| --- | --- |
| `p1` | Blocks core use, security, data loss, or a named near-term milestone |
| `p2` | Normal planned work |
| `p3` | Polish or nice-to-have |

| State | Meaning |
| --- | --- |
| `ready-for-agent` | Well specified, implementable |
| `ready-for-human` | Needs a human decision, design, or manual work |
| `needs-info` | Too vague to prepare |
| `needs-triage` | Unsure, or possible duplicate |

| Route | Spec Kit work |
| --- | --- |
| `specify` | New capability: specify, self-answered clarify, plan, tasks, in a new `specs/NNN-*` directory |
| `converge` | Change to an existing feature: amend `spec.md`, append a `## Phase N: Convergence` section to `tasks.md` |
| `none` | No spec work (docs, design assets, questions, spikes, small chores) |

The route is always forced back to `none` if the state is not `ready-for-agent` (for example `needs-info`), regardless of what the model or a maintainer-set type would otherwise suggest — prep never starts for an issue that is not ready. When a maintainer manually overrides the type to `bug` or `chore` on a non-model (heuristic) classification, the route is re-derived exactly as the heuristic itself would have chosen it: `converge` if the text references the existing spec, `none` otherwise — a model classification's own route stands as-is, since only the model actually read the issue body to judge scope.

**Stage 2: prep** is split into three jobs so the agent itself never holds write credentials:

1. **`triage`** (after classification) sets a single `prep` output to `true` only when *all* of: the route is `specify` or `converge`, the state is `ready-for-agent`, the issue author has **real write access** (see below), and `ANTHROPIC_API_KEY` is configured. When `prep` is true it also exports the issue to `.triage/issue-<N>.md` (the untrusted title/body wrapped between two `~~~~<random-nonce>` marker lines, never interpolated into a shell) and uploads it as the `issue-export` artifact.
2. **`prep-agent`** (`needs: triage`, only runs when `prep` is `true`) checks out the **default branch** fresh — its ref pinned explicitly to `${{ github.event.repository.default_branch }}` rather than assumed from the trigger, and never an existing `triage/issue-<N>` branch, whose `.omp/commands`, `.specify/scripts`, `CLAUDE.md`, or `.claude/settings.json` a previous agent run could have altered — downloads the issue export, and runs `anthropics/claude-code-action` following `.github/triage/prompt.md`. This job has **`contents: read` only, no `GH_TOKEN`/`GITHUB_TOKEN` at the job level, and runs no git commands at all**: it cannot push, comment, or label anything. Its tool access (`claude_args --allowedTools`) is scoped to `Read(./**)`, `Glob`, `Grep`, `Edit(specs/**)`, `Edit(docs/**)` (which also governs the Write tool — Claude Code ignores path-scoped `Write(...)` rules, so this is the only way to scope file creation too), and `Bash` pinned to exactly five Spec Kit PowerShell scripts, each as an exact-prefix-plus-space rule.
3. **`publish`** (`needs: [triage, prep-agent]`, `contents: write`, `issues: write`, `pull-requests: write`) does a fresh checkout of the **default branch** (ref pinned the same way), downloads `prep-output` into a temp directory outside the repo, and runs `node .github/scripts/prep-guard.mjs apply <dir>` while the tree is still that known-good checkout and before any branch exists — so the guard's "is this unchanged from a trusted copy" check (needed because the whole tree was uploaded, including non-markdown files like `docs/spike/*.mjs`) can never be satisfied by comparing against a branch a prior run might have tampered with. The guard allows only regular, non-symlink files matching `specs/<NNN-kebab-name>/**/*.md` or `docs/**/*.md`, under 1 MiB each, capped at 2000 entries (the whole specs/+docs/ tree, not a diff). `publish` then **always creates `triage/issue-<N>` fresh** from that checkout — never by switching onto a previous run's branch tip, which would make `git switch` try to reconcile the guard's already-applied changes against whatever that branch already had and abort whenever a second run touches the same lines — and pushes with a compare-and-swap (`git push --force-with-lease`, leased against the branch's actual current remote SHA from a just-fetched `git ls-remote`). Each run regenerates the branch from the default branch and replaces whatever prep commit was pushed before; an existing open PR for the branch is reused (`gh pr list`) rather than recreated, since the PR tracks the branch name, not a specific commit.
4. **`notify-failure`** (`needs: [triage, prep-agent, publish]`, `issues: write`) comments a link to the failing run on the issue whenever `prep` was `true` but `prep-agent` or `publish` failed.

The triage comment itself explains when prep is skipped — missing secret, author without write access, or state not yet `ready-for-agent` — rather than unconditionally promising "prep will run".

### Trust: real write access, not just author association

`author_association` (`OWNER`/`MEMBER`/`COLLABORATOR`) is necessary but not sufficient: a read-only collaborator still carries the `COLLABORATOR` association. `trusted` additionally requires `GET /repos/{repo}/collaborators/{login}/permission` to report `admin`, `maintain`, or `write` (an `OWNER` author skips this call — ownership always implies write access). Any API error (including a 404 for a non-collaborator) fails closed to "not trusted".

### The `.specify/feature.json` decision

`.specify/feature.json` is gitignored machine-local state (see `.specify/.gitignore`) used by Spec Kit's PowerShell scripts to remember which feature directory is active across invocations. It is never part of the guard's allowlist and never committed or published:

- For `specify`, `create-new-feature.ps1` writes it itself (a plain file write from the script process, not through Claude's Edit/Write tool permissions) so the rest of the same job's `clarify`/`plan`/`tasks` invocations find the feature it just created. It never leaves the ephemeral `prep-agent` job.
- For `converge`, there is no new feature to create `feature.json` for; instead, the `triage` job resolves the issue's `spec:NNN` label against the real `specs/` directory listing, falling back to `specs/001-core-session-workspace` when no label is present and that directory exists. Because the agent's shell access is limited to specific script invocations (not a general shell), it cannot read its own process environment either, so the resolved path is handed to it twice: as the `SPECIFY_FEATURE_DIRECTORY` environment variable for Spec Kit's own scripts (which already treat that as the highest-priority, explicit override — see `.specify/scripts/powershell/common.ps1`), and as a literal `FEATURE_DIRECTORY=` line in the agent's own prompt text, which is the only way to get the value into the agent's own reasoning. No file needs to be written or committed either way.

## Setup

| Item | Needed for | How |
| --- | --- | --- |
| Nothing | Stage 1 with the keyword heuristic | Works today with the default `GITHUB_TOKEN` |
| `ANTHROPIC_API_KEY` secret | Model classification (stage 1) and all of stage 2 | `gh secret set ANTHROPIC_API_KEY` |
| **Allow GitHub Actions to create and approve pull requests** | Automatic draft PR | Repository **Settings > Actions > General > Workflow permissions**. Without it, `publish` pushes the branch and comments a compare link. |

GitHub Models is retired, so there is no credential-free model option. Without the key, classification uses a deterministic keyword heuristic that never sets `area`. The comment says which method ran. To change the model, set the repository variable `TRIAGE_MODEL` (default `claude-haiku-4-5`).

## Run it manually

```sh
gh workflow run issue-triage.yml -f issue_number=90 -f force=true
```

Dry run locally (classifies and prints, writes nothing):

```sh
GITHUB_TOKEN=$(gh auth token) GITHUB_REPOSITORY=<owner>/<repo> ISSUE_NUMBER=90 DRY_RUN=true node .github/scripts/triage.mjs
```

Run the unit tests with `node --test .github/scripts/triage.test.mjs`. The workflow runs them before every triage.

## Security notes

- Untrusted issue text is never interpolated into a `run:` script. `triage.mjs` reads it over the REST API. `prep-guard.mjs export` writes it to `.triage/issue-<N>.md` wrapped between two `~~~~<random-nonce>` marker lines and tells the agent to treat everything inside as data, never instructions — the nonce is regenerated every run so the issue body can never forge its own closing marker.
- The agent that handles untrusted issue content (`prep-agent`) never holds a write-capable token, never holds `GH_TOKEN`/`GITHUB_TOKEN` at the job level, and runs no git commands; the job that has write credentials (`publish`) never runs the agent and never parses untrusted issue content — it only validates and copies already-produced files.
- `prep-agent` always checks out the default branch fresh, never a possibly agent-influenced `triage/issue-<N>` branch from an earlier run, so a compromised prior run can never propagate its own tampered `.omp/commands`, `.specify/scripts/powershell/*.ps1`, `CLAUDE.md`, or `.claude/settings.json` into the next one.
- The agent's tool allowlist is scoped, not a bare `Read`/`Write`/`Edit`: `Edit(specs/**)` and `Edit(docs/**)` (which also governs the Write tool), `Read(./**)`, bare `Glob`/`Grep`, and `Bash` pinned to exactly five Spec Kit PowerShell scripts, each as an exact-prefix-plus-space rule (`Bash(pwsh .specify/scripts/powershell/<script>.ps1 *)`) so the rule cannot be satisfied by a different command that merely starts with the same prefix.
- A deterministic guard (`prep-guard.mjs apply`) — not git state, which the agent's own tree could have manipulated — is the sole authority for what gets published. It rejects any symlink, any path with a `..` segment or a leading `/`, any file over 1 MiB, more than 2000 total entries (the whole specs/+docs/ tree is uploaded, not a diff), and anything that is not a regular file matching `specs/<NNN-kebab-name>/**/*.md` or `docs/**/*.md` — closing the gap where a bare `docs/**` allowlist would have covered runnable code such as `docs/spike/*.mjs`/`*.ts`, or where `.specify/feature.json` would have let the agent plant an absolute or traversal path.
- `publish` always creates `triage/issue-<N>` fresh from its own default-branch checkout and pushes with `git push --force-with-lease`, leased against the branch's real current remote SHA (`git ls-remote --exit-code`, distinguishing "branch absent" from a genuine network/auth failure before ever touching it) — never by switching onto whatever that branch already had, which both avoids depending on a possibly agent-influenced branch's tree and sidesteps `git switch`'s checkout semantics aborting whenever a second run touches the same lines. Each run replaces the previous prep commit outright; an existing open PR for the branch is reused rather than recreated.
- All three `actions/checkout` steps pin `ref: ${{ github.event.repository.default_branch }}` explicitly rather than relying on the triggering event's ref, so a `workflow_dispatch` invoked from a non-default ref can never substitute an untrusted reference tree for the scripts, the guard, or the push target.
- `notify-failure` fires on both `failure` and `cancelled` for `prep-agent`/`publish`, not only `failure`, so a cancelled run still gets a visible comment on the issue instead of silently going unnoticed.
- Git pushes use a step-scoped `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0` credential injection, never a token embedded in a URL or passed to `git` as a command-line argument (which would otherwise be visible in the runner's process list/base64-decodable from it).
- Third-party GitHub Actions (`actions/checkout`, `actions/setup-node`, `actions/upload-artifact`, `actions/download-artifact`, `anthropics/claude-code-action`) are pinned to full commit SHAs, not moving tags, with a `# vN` comment for readability; Dependabot (`.github/dependabot.yml`) opens weekly update PRs for them.
- `trusted` requires both `author_association` in `OWNER`/`MEMBER`/`COLLABORATOR` *and* a live `GET .../collaborators/{login}/permission` check reporting `admin`, `maintain`, or `write` (OWNER skips the call). Any API error fails closed.
- Permissions are least-privilege per job: `triage` has `contents: read`, `issues: write`; `prep-agent` has `contents: read` only; `publish` has `contents: write`, `issues: write`, `pull-requests: write`; `notify-failure` has `issues: write` only.
