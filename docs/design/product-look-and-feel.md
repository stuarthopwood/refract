# Product look and feel

Decided by Stuart in the #474 grill, 2026-10-08.

This page covers Refract's old `docs/DESIGN.md` "Look and feel" section, reproduced verbatim: theme, density, fonts, state colour roles, the shared status icon, the brand watermark, scrollbars, square choice items, chat text colour, the active/selected indicator, metadata iconography, tooltips, and the no-brackets copy rule. Items marked **(default)** were the doc author's proposals that Stuart had not yet reviewed when this text was first written. Two stale duplicate bullets from the old section are not repeated here; they stay in [implementation-notes.md](implementation-notes.md#superseded-or-restated) (Superseded or restated).

## Look and feel

- **Theme** (spec 007): dark only (Stuart, 2026-10-02: "I don't think I want a light mode"). Two built-in presets at the time this page was first written, Dark and Dark (high contrast); a third, **Obsidian** (#550, theme foundation palette v2, PR #596), has since shipped, picked from the Settings screen's Appearance section: every preset shown by name and swatch, the active one marked in text and colour, choosing a different entry repaints the whole app immediately while Settings is open, and only Save persists the choice -- Cancel, Esc, or leaving Settings reverts to whichever theme was active before. No OS light/dark follow, since there is nothing to follow between all-dark presets.
- **Density**: medium. Neither terminal-tight nor roomy chat-app.
- **Fonts**: two independent, user-customisable settings.
  - **UI font** for the app chrome.
  - **Code font** for code blocks, tool output, diffs, and the message box: monospaced, with Nerd Font glyph support and a ligatures on/off choice, and a size setting.
  - **(default)** The UI font defaults to bundled Geist and the Code font to bundled Geist Mono (issue #1246); otherwise Refract uses fonts installed on the system; glyphs missing from the chosen font fall back to another installed font.
  - **Exception**: the "Refract" wordmark and tagline on the Readiness screen's brand header use one bundled display font (Geist, `src/renderer/assets/fonts/`): the wordmark at weight 700/48px, the tagline lighter. It is not a UI font or Code font setting and is never used for body text. The app icon itself (`build/icon.ico`) is a separately authored image asset, not rendered from this font.

  _Superseded by #4 (2026-10-07): the two-font split (UI, Code) above is replaced by three roles (App, Chat, Code); see [foundations-typography-spacing.md](foundations-typography-spacing.md#font-roles)._
- **State colour roles** **(default)**: working (accent), idle (muted), needs you (warning), stopped (error), Unread response (info). Every state also has a distinct icon, so colour is never the only signal. The `working` role's accent colour (`--state-working`) is still used by `SubagentPanel.tsx` and `Transcript.tsx`'s own state icons; the shared `StateIcon` component's own `working` icon (below) is the one exception, rendering the agent-working spinner's own per-theme component token `--agent-spinner-core` instead (issue #612) rather than this accent token.
- **Shared status icon** (Stuart, 2026-10-04; extends State colour roles above): every surface that shows a session's live status -- session list, chat header, session details card -- renders through the one shared `StateIcon` component (`src/renderer/features/sessions/sessionDisplay.tsx`): the agent-working spinner, animating, for working (`AgentSpinner`, `src/renderer/components/brand/AgentSpinner.tsx`, issue #612, supersedes `BrandSpinner`/spec 011), a check in a circle for idle, a bell for needs-you, a square for stopped. **Unread response** (issue #731, 2026-10-15, ui-architect-v3 roundtable): a display-only status -- idle with an unseen reply, never a stored status -- drawn in idle's place as a speech bubble with a tail, in a new `--state-unread-response` token aliasing the existing `--severity-info` role (the first session state that role covers), distinct from needs-you's amber; the trailing amber dot this status used to show is gone. No surface draws its own plain filled dot, or any other shape, for a state `StateIcon` already covers.
- **Brand watermark** (spec 012): a faint, single-colour silhouette of the Refract mark, anchored to the bottom-right corner of the chat area's reading area (never the composer), on by default and toggled off (or back on) from a switch in the Appearance section. Exactly one instance shows at a time -- the single chat pane, or the right pane of a split, never both -- and it is hidden outright on the Settings, Readiness, and (once built) Manage sessions screens, and whenever Windows High Contrast or reduced transparency is on.
- **Scrollbars**: thin, drawn from theme colours (`--scrollbar-thumb`, `--scrollbar-thumb-hover`, `--scrollbar-track`), and `color-scheme` follows the theme so no default light scrollbar appears on dark.
- **Square choice items**: options in pickers and menus, tabs, toggle segments, the selected session row, and conversation rows have square corners (one rule in `globals.css`); buttons, inputs, popups, dialogs, cards, and chips keep their rounding.
- **Chat text colour** (Stuart, 2026-10-04): primary chat prose (user and assistant message text) uses a dedicated `--chat-foreground` token, a perceptibly dimmer light grey, visibly softer than `--foreground` (`oklch(0.985 0 0)` in the dark theme, which reads as indistinguishable from pure white against the dark background and is too harsh for body prose) while staying well clear of `--muted-foreground` (`oklch(0.708 0 0)`, reserved for secondary/meta text such as branch names, timestamps, and captions). No chat surface sets an explicit white value, uses the bare `--foreground` token, or uses any token brighter than `--chat-foreground` for prose.
  - **Amended (Stuart, 2026-10-19 to 2026-10-20, #1039):** Cyber Amber's surfaces (`--background`, `--sidebar`, `--card`/`--popover`/`--surface-1`/`--surface-2`, `--surface-3`/`--muted`/`--accent`/`--secondary`, `--border`, `--input`) became PURE neutral greys, chroma 0, byte-identical to Default Dark's own surface tokens (`#0a0a0a`/`#171717`/`#262626`/`#747474`) -- replacing this preset's own original brown canvas. The accent moved to a vivid orange (`--accent-text` `#fb923c`, `--primary`/`--send` `#c2410c` with white text) and the warning hue shifted from 75 to 88 to stay visibly distinct from the new, closer-hued accent. **Text softening (retuning `--foreground`/`--chat-foreground` softer, in Default Dark and Cyber Amber) was ALSO tried as part of #1039, through three same-day corrections, then reverted entirely (Stuart, 2026-10-20): it moved to a separate, new, app-wide issue instead.** `--foreground`, `--chat-foreground` and `--muted-foreground` in both themes stay at the values documented in this bullet's own parent paragraph above, untouched by #1039. **Gate round 1 fix:** `--ring`/`--sidebar-ring`, `--scrollbar-thumb`/`--scrollbar-thumb-hover` and `--composer-focus` are now also byte-identical to Default Dark's own literals (an earlier draft of this bullet wrongly called `--ring` part of the accent family -- it stays achromatic, the 2026-10-09 rule, and never carried the orange). **Gate round 2 decision:** the new accent also closed Cyber Amber's own accent-vs-`--severity-error` distinctness gap below the 1.5:1 floor #551's gate established -- no single value clears both that floor and the error-text floor at once, so `--severity-error`/`--destructive`/`--state-stopped`/`--pr-closed` retune to `oklch(0.665 0.12 22)` (the best achievable swatch ratio, 1.42:1), an accepted departure (`docs/design/accessibility.md` "Accepted departures"), scoped to Cyber Amber only. Only the accent family (`--accent-text`, `--primary`/`--send`, markdown links), the warning hue, the error family, and `themes.ts`'s own `swatchPrimary` differ between Cyber Amber and Default Dark. See `globals.css`'s own `.theme-cyber-amber` header comment for the full rationale and every measured ratio. `scripts/check-theme-contrast.mjs`: 872/872 pairs across 5 themes PASS (up from 839 after the #1050/#700/#464 merge; #1039 itself changed no PAIRS entries, only Cyber Amber's own literal values). **Landed (#1074, Stuart 2026-10-20, spec 007 FR-023):** the "separate, new, app-wide issue" above is #1074 -- `--foreground` (and every alias that resolves to it: `--card-foreground`, `--popover-foreground`, `--secondary-foreground`, `--accent-foreground`, `--sidebar-foreground`, `--sidebar-accent-foreground`) moves to white at 90% alpha, `--chat-foreground` to 78%, `--muted-foreground` to 60%, each composited over the surface it actually sits on, in Dark, Obsidian, Nordic Frost and Cyber Amber; Dark (high contrast) stays solid, untouched. A foreground on a COLOURED fill (`--primary-foreground`, `--send-foreground`, `--destructive-foreground`, `--sidebar-primary-foreground`, every `--state-*-foreground`/`--pr-*-foreground`, and `--composer-selection-fg`) stays a solid, opaque literal. `scripts/check-theme-contrast.mjs`: 887/887 pairs across 5 themes PASS; live-verified (`scripts/verify-1074-text-opacity.mjs`, draft PR #1104).
- **Active/selected indicator** (Stuart, 2026-10-04: fixed the token split below): wherever the app marks the current/selected/active item -- the visible session row, a conversation-history entry, the Manage sessions Active/Archived segmented toggle -- it uses the same treatment: a 2px left-edge accent border/bar in one shared `--active-indicator` token (`bg-active-indicator` inside the session list, `border-l-active-indicator` elsewhere), so every surface resolves to the identical colour rather than two merely similar-looking ones. The Manage sessions screen's Active/Archived segmented toggle uses the same token through an inset-shadow variant instead (`shadow-[inset_2px_0_0_0_var(--color-active-indicator)]`, not a `border-l`), since adjacent `ToggleGroup` segments share edges rather than each owning their own left border. The neutral `--border` token marks a row's resting-state outline only and never doubles as the selected-state signal. **Narrowed for dropdown menus** ("Decided (Skippy, delegated by Stuart 2026-10-15)", gate round 7, PR #877 issue #564 comment -- overturns this rule's own "a dropdown's checked option" example, kept in every OTHER menu-free surface above): once every dropdown menu's active-row highlight became this SAME `--active-indicator` bar (gate round 5), a menu's own permanently-marked current/checked option (e.g. the Theme submenu's active preset) read as indistinguishable from plain keyboard focus on a DIFFERENT row. In a dropdown menu specifically, the bar follows focus, never selection; a real `menuitemradio`'s own leading ring-and-dot mark (`aria-checked`, issue #1043, 2026-10-20 -- the shared `DropdownMenuRadioItem`, the Theme submenu and the composer's Reasoning picker both draw it the same way) marks which option is actually current instead, never a trailing check icon or the word "Current" any more. This narrowing is Stuart-delegated, not yet Stuart's own direct sign-off, and may be overturned.
  - **Exact shape, decided (Stuart 2026-10-21, #1122, grilled, none deferred):** every PERSISTENT selected item (as opposed to the dropdown/menu keyboard-focus case narrowed above, unaffected) is square-cornered and the bar itself is flush full height (`inset-y-0`, no rounded caps, 2px wide) -- never the inset, rounded-pill shape some copies had drifted to. The call sites (the "Pull requests" nav entry, Session rows and the collapsed Project group header's own containment cue in `SessionList.tsx`/`SessionRow.tsx`/`GroupHeader.tsx`, the Settings nav in `SettingsScreen.tsx`, PR list rows in `PullRequestRow.tsx`, Explorer rows in `FileExplorerPanel.tsx`, Manage sessions rows in `ManageSessionRow.tsx`, and the Subagent panel in `SubagentPanel.tsx`) now all render the bar through one shared `ActiveIndicatorBar` component (`src/renderer/components/ActiveIndicatorBar.tsx`), replacing the hand-copied span each site used to carry, each with its own forced-colours fallback (not just some); every site but the collapsed group header (bar only, #735 decision 22, unaffected) also gains the accent fill (the Subagent panel's own #563 decision 13 bar-only exception is superseded).
- **Metadata iconography**: every piece of metadata shown in a tooltip, hover card, or compact info row -- status, repository, branch, worktree path, model, files changed, and the like -- gets a leading icon; bare text labels are not used for structured data of this kind. Actionable buttons inside a tooltip or card are right-aligned (trailing edge), never stacked at the left.
- **Tooltips** (Stuart, 2026-10-05, ui-architect-v3 review): a tooltip uses the same elevated `--popover` surface, border, and shadow as menus (never an inverted near-white bubble on the dark theme), floats 6px off its trigger with no arrow, and a `Kbd` inside it uses its normal key-cap colours.
- **No bracket/parenthetical UI copy** (Stuart, 2026-10-04): composer placeholder text and inline metadata rows never wrap supplementary information in parentheses or literal brackets (e.g. not "Message the agent… (/ for commands)"); use a leading icon, or a visually distinct but unbracketed treatment, instead.
