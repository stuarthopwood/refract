# Refract design

Look, feel, and interaction rules shared by every spec. Vocabulary is in [CONTEXT.md](../CONTEXT.md); behaviour is in `specs/`; rules are in the [constitution](../.specify/memory/constitution.md). Ideas and features are tracked as GitHub issues (see [Backlog](#backlog)).

Items marked **(default)** are my proposals that you have not reviewed yet.

## Principles

- Show state at a glance; never make the developer open a Session to learn whether it needs them.
- A dense turn stays readable: many tool calls must not bury the answer.
- Every action has a visible button; shortcuts are a second way, never the only way.
- Destructive actions name what will be lost before they happen.
- The agent does the work; Refract is the place to watch, steer, and approve it.

## Layout

- Three regions: **session list** (left), **chat** (centre), and a right region for Subagents and (later) changes/files/side chat. Spec 004 gives it its first occupant: collapsed to zero width (`collapsedSize={0}`, permanently mounted rather than conditionally rendered, so `react-resizable-panels` never recomputes sibling widths on open/close) until the **Subagents** chip opens the **Subagent panel**; closing it collapses the pane back to zero width and leaves the chat pane's own size and scroll exactly as they were (pixel-measured, not by eye).
- **Split chat pane** (spec 005 FR-001 to FR-023): the centre region shows one **Chat pane** (a full Session's chat) or two, side by side, separated by a draggable **Divider** (a `react-resizable-panels` `ResizableHandle`, keyboard-operable, position persisted via `Settings.split`); **Open in split** (a session row's menu item, or Ctrl+click the row) turns one pane into two. Exactly one pane is **Focused** at a time -- a left-edge accent bar plus a visible "Focused" text badge on its header, never colour alone -- and it is the one every session-row click, the message box, Stop, the queue, and approvals act on; clicking or typing inside a pane focuses it, and **Ctrl+Shift+\** (or a small focus-move button on the divider handle) moves focus to the other pane without the pointer. Each pane has its own close control (`[A, B] -> [survivor]`, full width); choosing a session already shown elsewhere focuses that pane instead of duplicating it (the same session is never shown in both panes at once). Below `2 × 360px` of chat-area width the pane collapse to one (the focused Session), with a small chip in its header naming the other (hidden) Session that swaps to it in one click, re-splitting automatically once the window is wide enough again. A split survives a restart (both Sessions, the divider position, and the focused pane restored, FR-014) without starting either agent -- each restored pane looks exactly like a never-opened Session until the developer actually opens it (sending a message, clicking its row, or choosing Open in split on it); a Session dropped from a restored split (deleted or archived) leaves the other at full width.
- The **Approval mode** pill sits directly above the message box, as the first item of its chip row (`ApprovalModePill.tsx`): the current mode's lucide icon and name, opening a square-cornered `DropdownMenu` of all three modes (Ask/Edit freely/Auto, each with its icon, name, and a one-line description of what it prompts for), the current one marked by a check icon and the word "Current"; a mode change waiting for the session to go idle shows on the pill itself ("Auto after this turn"); both the pill and its menu are fully keyboard-operable, and the pill's accessible name states the current mode.
- A **status bar** along the bottom carries the low-memory warning and (once spec 006 ships it) the update badge; the Approval mode switch that used to live here moved to the pill above (spec 001 T098). The status bar itself is not yet removed -- that is spec 001 T099, which waits on spec 008's profile item to exist first (its own foundational phases are substantial, not a quick slice); until T099 lands the status bar keeps running along the bottom exactly as before, just without its Approval mode control.
- The **title bar is merged into the app's own top row** (spec 001 T100): the window has no native frame or menu bar at all. The left nav's header (the Refract icon and its name) starts at the very top of the window, and the chat header sits beside it; together they form the app's top row, draggable to move the window (every button, input, and menu inside them stays clickable), with a double-click on the draggable area maximising or restoring the window, and the top-right of the row always reserved for the window's own minimise/maximise/close buttons, painted in the active theme's colours (dark only today). The native menu does not reveal while Alt is held once the title bar is merged this way -- confirmed live against a real interactive desktop with a working framed-window baseline in the same run, not assumed (`docs/spike/FINDINGS.md` item 33, correcting the earlier inconclusive item 24) -- so Refract draws its own File/Edit/View/Window menu bar instead: a standalone Alt tap shows it (never a combo like Alt+Tab), Esc or a click away hides it, and every item opens the one real Electron application menu, so copy, paste, undo, redo, zoom, and (in development) reload and developer tools all keep working by their usual keyboard shortcut whether that bar is shown or not.
- Panes resize by dragging their borders; the session list can be hidden -- its panel collapses to zero width but its content stays mounted, marked `inert` and `aria-hidden` rather than unmounted, so the Sessions nav's own open groups, scroll position, and any in-progress rename survive being hidden and shown again; focus-fallback helpers (`src/renderer/lib/focus.ts`) treat a stale `inert` ancestor the same as absence from the DOM.
- Session list: collapsible group per **Repository**, **Sessions** sorted by most recent activity. Each row shows a state icon, the Session name, its branch, time since last activity, and an unread dot. Hovering a row's open button, or giving it keyboard focus, opens a **details card** after about 750 ms (stays open while the pointer is over the card, dismissed by Esc, never covers the row, suppressed while that row is renaming): the state icon and status label, the relative last-activity time, the repository (folder icon), the branch (with the Base branch as muted "from <base>"), the worktree's absolute path (wraps, muted, marked "(missing)" instead of showing a stale one when the worktree is gone), the files-changed count from `sessions.diffStat` ("Counting changes…" while it loads, then "N files changed +A -D", or "partial" past the 200-file/1 MiB-per-file cap, or muted "Not available" when the worktree is missing or the count could not be computed), and **Copy path**/**Open in file explorer** buttons (`sessions.revealWorktree`); the same two actions are mirrored on the row's `⋮` menu since Radix hover cards are not keyboard-reachable. The provider/model/reasoning-effort readout (T062's `lastModel`/`lastThinkingLevel`, "Model not known yet" when absent) sits between the worktree path and the files-changed count. **Archived** Sessions sit in a collapsed group at the bottom of each Repository. Each Repository header has two buttons: **+** creates a Session from the default branch in one click (tooltip "New session from <default branch>"), and the branch icon opens the Base branch picker with the default branch preselected (tooltip "New session from a branch…"); either way the new Session is selected and opened. The picker opens below its field and lists two groups: **Branches** (default first) and **Sessions** (each Session's display name, its branch id, and an **Archived** tag for archived Sessions). Right-clicking a row's card opens the same options menu as its `⋮` trigger (a shared `ContextMenu`, never a second menu to keep in sync).
- Chat header: Session name and branch, and a Conversation switcher (history of that Session's Conversations); the pending-Approval-mode chip that used to live here moved to the Approval mode pill above the message box (spec 001 T098). The header is also the right half of the app's merged top row (see above).
- **Session readout chip row** (spec 004 FR-001 to FR-010, FR-021): directly after the Approval mode pill above the message box, each entry read via `ReadoutChip.tsx`'s shared baseline (icon slot, a plain phrase when not interactive, a real `<button>`/`<a>` with an accessible name and a visible focus ring when it is); which show is chosen per-kind in Settings (below), live for every open Session, hidden entirely or reading "Not available" per its own rule, and the row wraps onto a further line rather than hiding a chip or overlapping the message box once the window narrows. **Changes**: "N files, +A -D" (abbreviated past 1000), or "Not available" when the worktree or Base branch is missing -- matches the session list's own details-card figure. **Context window usage**: "N/M tokens (P%)", hidden when the agent never reports it at all, "Not available" when a reading was expected and never arrived, and a visible warning (a triangle-alert icon plus the literal word "high", never colour alone) once usage reaches 90%. **Turn time**: ticks once a second while a turn runs ("28s", "1m 14s"), hidden otherwise. **Current time**: a pure client clock updating at the top of each minute, off by default, with no `aria-live` region (so the routine tick is never announced) and a static accessible name read only on focus. **Pull request**: "#N" for the Session's branch's open pull request on GitHub (`gh pr list`, no stored token), hidden when there is none, no remote, or `gh` is unavailable, with no error toast either way; activating it is a real external link (`target="_blank"`, the same `setWindowOpenHandler`-to-`shell.openExternal` path `Markdown.tsx` already uses for links in agent text, not a new IPC call) opening the real pull request in the system browser, accessible name "Open pull request #N". **Subagents**: the current turn's running-or-finished count (failed excluded), hidden before a turn has started any, activating it opens the Subagent panel below. **Todo progress**: "Todo N/M" from the agent's own task list, hidden when it has none.
- **Settings screen** (spec 004 FR-011 to FR-016): reached via the profile item's cog (spec 008 FR-002, below) replaces the session-list-plus-chat view with a left-section-list layout; two sections today, **Session readout** (all seven chip kinds above with their own on/off switch, each applied live) and **Appearance** (spec 007's theme picker, live preview, Save/Cancel). A **Back to chat** icon button returns to the session list and chat.
- **Profile item** (spec 008 FR-001 to FR-007, FR-018 to FR-024, `ProfileItem.tsx`/`ProfileMenu.tsx`; UI review, Stuart 2026-10-05, ui-architect-v3; post-build review fixes, Stuart 2026-10-05): pinned at the bottom of the session list, below its scrollable area -- the active GitHub account's round avatar and display name (a shared `initials` fallback, `src/renderer/lib/initials.ts`, while the avatar is loading, failed, or unset), and a separate **cog** button beside it. The name button is 40px tall and the cog 32px, filling the full 48px bar with no dead click band above or below either. Five sign-in states, each icon plus text, never colour alone, and each with an accessible name that starts with its own visible text (WCAG 2.5.3): **loading** (disabled while the first account read is in flight, name "Checking GitHub sign-in"); **signed in** (the account's avatar and display name, `@login on <host>` as the name tooltip); **GitHub CLI missing** (a "?" avatar fallback, name "GitHub CLI missing", FR-014); **GitHub unavailable** (a `gh-failed`/thrown-invoke read with nothing cached -- an amber triangle avatar fallback, name "GitHub unavailable", reachable only through the profile menu's own "Check again"); and **needs attention** (the active account's own GitHub sign-in problem, `state !== 'success'` -- an amber triangle icon beside the name, the accessible name appending "{name}, GitHub sign-in needs attention" for an expired/other credential problem or "{name}, can't reach GitHub" for an unreachable host, `account.problem === 'unreachable'`). Selecting the avatar/name part anywhere opens the **profile menu** (a `DropdownMenu`, `w-64`, `max-h-(--radix-dropdown-menu-content-available-height)` with its own scroll, so a very short window scrolls the menu instead of flipping or shifting it) upward (`side="top"`, 6px offset), items depending on GitHub sign-in state. Signed in: a two-line identity card (display name, then `@login on <host>`, or -- when the active account's own sign-in needs attention -- the same warning icon next to the name and "GitHub sign-in needs attention"/"Can't reach GitHub" in place of the host line); when it needs attention, a conditional **Fix sign-in…** (or, for an unreachable host, **Check GitHub connection…**) item follows immediately, opening Manage accounts and focusing the active row's own recovery button (Sign in again, or Check again) without starting any sign-in itself; then a separator; **Manage accounts** (`UsersIcon`); **Manage sessions** (`LayersIcon`), opening the dedicated cross-repository sessions screen (below); a separator; a **Theme** submenu (`PaletteIcon`) listing every built-in preset from `THEMES` with the exact same data-driven swatch `ThemePicker.tsx` already uses (each theme's own real background colour, never a hard-coded hex, `size-4` to match the Appearance settings icon), the active one marked by a check icon, the word "Current", AND the same shared 2px `--active-indicator` bar every other current/selected surface in the app uses (never colour alone); opening the submenu by keyboard moves focus straight to the active preset (a controlled `open`/`onOpenChange` plus a ref, checked only when focus is already inside the submenu, so a pointer-hover open is left alone) -- Radix's own default of focusing the first item only looked right while "Dark" (the first preset) was also current. Choosing a different one applies and persists at once through `useThemeStore`'s `save` (a menu is a transient overlay -- live preview with Save/Cancel stays Settings' Appearance section's job alone; a save that throws is caught and toasted the same way, never left unhandled), then a separator and **Appearance settings…** opening that section (which unmounts ProfileItem entirely, so focus goes to Settings' own first control, not back to the name button); **Keyboard shortcuts** (`KeyboardIcon`) -- an **update entry** slot is reserved right after it, deferred until spec 006 ships `updates.get()`/`updates:changed` (no part of that spec exists yet); **Health check** (`ActivityIcon`); **What's new** (`SparklesIcon`, trailing `ExternalLinkIcon`); a separator; then a destructive **Sign out** item for the active account. Signed out: an enabled **Sign in to GitHub…** item (`LogInIcon`) that opens Manage accounts AND starts the add-account flow immediately (there is nowhere else signed-out to show the flow's one-time code), **Manage accounts**, **Manage sessions**, a separator, then the same Theme/Keyboard shortcuts/Health check/What's new group (no Sign out, nothing is signed in). GitHub CLI not installed: an **Install GitHub CLI** link item (leading `DownloadIcon`, trailing `ExternalLinkIcon`, matching What's new's own icon placement), **Manage accounts**, **Manage sessions**, a separator, then that same group. GitHub unavailable (a `gh-failed`/thrown-invoke read): a "GitHub unavailable" item in Sign in's place (amber triangle, or a spinner plus "Checking…" while a refresh already runs), its trailing text reading "Check again", selecting it re-reads every account; then the same Manage accounts/Manage sessions/Theme/Keyboard shortcuts/Health check/What's new group. GitHub sign-in status still loading: a disabled **Checking GitHub sign-in…** item (`LoaderCircleIcon`, spinning) in Sign in's place, then the same group -- so a slow or hung `gh` call never hides Health check, the one diagnostic tool that could explain why. **Manage sessions** never depends on GitHub sign-in state, so it appears identically in every variant, and this shared block (Manage accounts through What's new) renders exactly once regardless of branch, so a `githubStatus` change while the menu is open can never remount it and drop focus. Arrow keys navigate the menu, including into and out of the Theme submenu; Esc closes it; focus returns to the profile item's name button on close. Every dialog the menu opens (Manage accounts, Sign out, **Keyboard shortcuts**, **Health check**) is mounted as a sibling of the `DropdownMenu`, each with its own explicit `onCloseAutoFocus` returning focus to that same name button -- none is given a `Trigger`, so Radix's own default close-auto-focus would otherwise drop focus to `<body>` (confirmed live, not assumed). Choosing a theme announces "Applied theme {name}", and a completed Sign out announces "Signed out {name}", through the one shared polite live region mounted here. Selecting the cog instead opens the Settings screen directly, without opening the menu; its tooltip names the Settings action, suppressed while the menu is open so the name tooltip and the menu never stack on the same trigger. Opening the menu no longer re-reads the account list itself (removed: unmounting the focused first row while a non-modal menu was open could drop focus to `<body>`) -- the list instead refreshes when Manage accounts opens, and whenever the window regains focus or the tab becomes visible again, throttled to once per 5 s and skipped entirely while a read is already in flight or an add-account/sign-in-again flow is waiting on the user.
- **Keyboard shortcuts dialog** (spec 008 FR-020, `KeyboardShortcutsDialog.tsx`, T023): a read-only list reachable from the profile menu, grouped under headings ("Message box", "Split view"), each row a plain-text action and its chord as `Kbd`/`KbdGroup` key-caps. Lists ONLY a chord individually verified to have a real working handler behind it (a keydown listener, a textarea default, or an Electron accelerator) -- several rows `docs/DESIGN.md`'s own "Keyboard" table below documents are left out because no such handler exists yet (tracked as a GitHub issue, not silently dropped or promised as "coming soon"). Initial focus lands on the primary **Done** button.
- **Health check dialog** (spec 008 FR-022, `HealthCheckDialog.tsx`/`CheckRow.tsx`, T024; post-build review fixes, Stuart 2026-10-05): reachable from the profile menu, re-running the exact same `readiness.check()` the first-run Readiness screen uses and rendering each row through the same extracted `CheckRow.tsx` (icon, the real `found`/`hint` text exactly as returned, never an invented string or hard-coded version) -- the one difference is the state word ("Passed"/"Passed with a warning"/"Failed"/"Checking") shown visibly here rather than `sr-only` as on the quieter first-run screen, announced only once (`CheckStatusIcon`'s own `sr-only` word is suppressed here so a screen reader never hears it twice). Pass/warning/fail are never colour alone: icon plus that visible word every time, using the same `text-state-needs-you`/`text-state-working` design tokens every other state surface in the app uses (not a hard-coded colour), so a warning here always matches the same warning elsewhere under every theme including high contrast. A re-run keeps the previous results visible, dimmed (`opacity-60`) and `aria-busy`, instead of blanking every row, so the dialog never shrinks and **Check again** (labelled "Checking…" while a run is in flight, a fixed minimum width so it never moves) never drifts out from under a pointer that just clicked it; it is `aria-disabled` (keeping focus) while the primary **Done** button stays enabled. A thrown `readiness.check` (not just a returned failure) is caught: every row is marked failed with the hint "The check could not run. Try Check again.", exactly like the first-run Readiness screen's own catch, and an assertive region announces "Health check couldn't run." A polite region announces "Checking…" at the start and, on completion, counts failures and warnings separately so a pass-with-a-warning row is never reported as a failure: "Health check complete. All checks passed." with nothing to report, "Health check complete. All checks passed, {m} with a warning." (plural "warnings" for m>1) for warnings only, or "Health check complete. {n} failed." plus ", {m} passed with a warning" (plural as above) when any check failed. Also updates the shared health store (`useHealthStore`) the same way the Readiness screen does, so the status bar's low-memory-adjacent OMP-version notice stays in sync. The dialog is `sm:max-w-lg` (matching the other dialogs here) so a wrapped state word never orphans onto its own line.
- **Manage accounts** (spec 008 FR-008 to FR-011, FR-014, FR-016, `ManageAccountsDialog.tsx`/`AddAccountPanel.tsx`/`SignOutDialog.tsx`/`OmpProvidersSection.tsx`, T016/T017/T019): a `Dialog` (`sm:max-w-lg`, capped at `min(680px, 100vh-4rem)` tall with its own outer scroll so a short window never clips it -- measured 680px at an 800px-tall window, 436px and scrolling at a 500px-tall window, the close button always reachable) reachable only from the profile menu. While the account list itself is first loading, the GitHub section shows a spinner and "Checking GitHub sign-in…", with no Add account button (nothing is known signed in or not yet); if that read fails outright (`gh-failed`, or a thrown invoke, nothing cached), it instead shows an amber warning icon, "Couldn't read your GitHub CLI accounts.", and a **Check again** button, again with no Add account button, since offering to add a new account before the existing ones can even be read would be backwards. Otherwise it lists every GitHub CLI account under a **GitHub accounts** section header with its own **Add account** button (primary when the list is empty, outline otherwise, disabled while an add flow runs). Each row: avatar, display name (second line: `@login` and the host, each with a leading icon), the active row marked by both a left accent border and an inline check-icon **Active** label (never colour alone) and offering only **Sign out**; every other row offers **Switch** (outline) and **Sign out** (ghost, destructive text); a row whose GitHub CLI auth state is not `success` additionally shows an amber warning-icon status line -- "Sign-in expired." for an expired credential, "Couldn't reach GitHub." for an unreachable host, or "Sign-in needs attention." for any other cause -- and, in its trailing action cluster (ahead of Switch and Sign out): on an unreachable host, a **Check again** button (re-reads every account, `aria-disabled` while already running); otherwise, on `github.com`, a **Sign in again** button (`aria-disabled` while an add/sign-in flow is already running; any other host instead gets a plain `gh auth login --hostname <host>` instruction line, since the add flow is github.com-only). **Switch** is pessimistic: the row shows a spinning **Switching…** state and the active marker moves only once the GitHub CLI itself confirms (the row is projected immediately from the pre-mutation account list plus the CLI's own exit code, without waiting on a second `gh auth status` read, so the profile item updates in well under 1 second in practice -- measured 0.75 to 0.95 s, FR-010/SC-002's 1 s budget -- while a background `gh auth status` read then reconciles with the CLI's real state a moment later and rebroadcasts if it differs), since switching changes the identity the next pull request or update request uses; every other row's Switch button disables meanwhile. Add account runs inline directly under the section header and above the account list (never a nested dialog, and never pushed off-screen by a long list): a spinner while starting, then (typically within about 0.5 to 1 s) the one-time code grouped as `XXXX-XXXX` (shown exactly as received if the CLI's own code is already hyphenated or a different length) in the code font, a **Copy code** button (never auto-copies the code; copies through the main-process clipboard channel, since the sandboxed renderer denies the Clipboard API permission outright), a link to `https://github.com/login/device` for a browser-less machine, and **Cancel** (the GitHub CLI's own device-flow process does not exit on its own while cancelling, so Cancel shows a disabled **Cancelling…** state, keeping focus rather than losing it, for about 2 seconds until the process actually ends); a failed attempt shows main's own plain-language failure reason as an alert (never a guessed cause), falling back to "Sign-in did not finish." when none is given, with **Retry** focused beside it. A completed add/re-auth flow announces "Added GitHub account {name}" or "Re-authenticated {name}" (or "Re-authenticated with GitHub" if no matching account could be found), appending " It is now the active account." whenever that flow changed which account is active, and moves focus to the new or re-authenticated account's own Sign out button. The first Esc while a flow is running cancels it instead of closing the dialog (a second Esc then closes it), and closing the dialog by any other means while a flow runs also cancels it. Sign-out confirmation (FR-011) is one shared `AlertDialog` reachable from here or from the profile menu's own Sign out item, naming the account and, when it is the active one, which account becomes active next (or that none will) before confirming; closing either dialog by any means always returns keyboard focus somewhere live -- the profile item's name button when launched from the menu, or the relevant Manage accounts row/button otherwise -- never `<body>`. No GitHub account signed in shows an empty-state message with **Add account** as the primary action; GitHub CLI missing shows an **Install GitHub CLI** link instead of the account list, with no Add account button. Below a decorative separator, a read-only **OMP provider sign-in** section (FR-016, research.md Decision 6 -- OMP has no `/login`/`/logout` over its own rpc-ui connection, so this never offers an in-app sign-in/out action and never mentions `/logout`): initial open shows a skeleton (three rows, "Checking OMP providers…", `aria-busy`) while a scratch `omp` process reads the list (measured 4.7 s direct, about 4 to 8 s end to end in the app) -- dialog-open focus stays on the GitHub section's Add account button throughout, never moving to this section. Loaded, it shows a summary line ("N of M providers signed in", or "All M providers signed in" -- measured "2 of 80 providers signed in" against a real OMP install), the signed-in providers always listed (their raw ids in the code font, a check icon, and "Signed in", never colour alone), the rest behind a collapsed "Show all M providers…" disclosure (toggling to "Show signed in only", focus kept on the toggle, the hidden rows in their own bounded, padded scroll region clear of the scrollbar), and a bordered instruction row ("run `omp login` in a terminal" -- `omp login` is the installed version's own documented terminal counterpart of `/login`) with its own **Copy command** button (same main-process clipboard channel as Copy code). Re-reads run only on dialog open, **Check again**, and **Retry** (both `aria-disabled`, not `disabled`, so focus is kept), never on a timer or window focus, since a read spawns that same multi-second process each time; a refresh with cached data to show keeps that data on screen with just a small "Checking…" indicator next to Check again (stale-while-revalidate) and a polite "OMP providers: N of M signed in" announcement on completion; a failed read keeps any cached list exactly as shown and adds its own inline error ("Could not read OMP providers") with **Retry** rather than losing what was already there.
- **Manage sessions screen** (spec 008 FR-025, FR-027, `ManageSessionsScreen.tsx`/`ManageSessionRow.tsx`/`ManageSessionsToolbar.tsx`, T026/T027/T028): reached from the profile menu's **Manage sessions** item (`LayersIcon`), swapping the main area for a dedicated cross-repository list, mirroring the Settings screen's own header (a drag region, a **Back to chat** icon button with its tooltip, and an `h1` focused on mount) plus a count line (`{n} sessions across {m} repositories`, counting only repositories that actually have sessions). A toolbar offers a search `Input` (name and branch, case-insensitive, Esc clears it), a repository `Select`, an archive `ToggleGroup` (**All** default, **Active**, **Archived**), and a sort `Select` (**Recently active** default, **Name, A to Z**, **Repository, A to Z**, **Status**). The selected archive segment uses the shared **Active/selected indicator** rule (above) through its inset-shadow variant, not a bright primary fill, and the filters live in the view store so they survive opening a session and coming back. Each row is a plain DOM list item (no virtualisation: 5 to 60 sessions), never one button nesting other buttons: a primary open button covers the whole info area as a five-column grid (`grid-cols-[6rem_minmax(8rem,24rem)_minmax(0,10rem)_minmax(0,9rem)_minmax(5rem,1fr)]`: status, name and branch, repository, a state cell, last activity) so the columns line up from row to row and the entire hover fill is clickable (`StateIcon` plus the visible status word, branch and repository each with a leading icon, archive state as a `Badge` with a leading icon and the word "Archived", a missing worktree shown as a leading alert icon and the words "Worktree missing"), beside a contextual quick-action button (**Archive**/**Restore**, with a tooltip and an in-flight guard) and a `⋮` menu (also with a tooltip) offering the identical action list (rename, open in split, copy worktree path, open worktree folder, archive/restore, stop agent, delete) the session list's own row menu builds, through one shared `sessionActions.ts` module both now call so the two lists can never drift apart; right-clicking a row opens the same list in a `ContextMenu` and F2 on the open button starts renaming, as in the left nav. Opening a row (or Ctrl+click for a split) follows the exact same `replaceFocused`/`open`/`openInSplit` path the session list uses, then returns to the chat view and moves focus into that session's own pane (the focused pane of a split, never another), and a short capture-phase click guard (about 500 ms) swallows the second click of a double-click so it cannot land on whichever left-nav row is now under the pointer. Archiving or restoring a row holds its own "Archived"/"Restored" announcement until the row's `⋮` menu (if the action was launched from it) has actually closed, so a screen reader is never told the outcome while the menu is still reading its own items; archiving or deleting a row that drops out of the current filter moves focus to the next row's open button, else the previous row's, else the search input, run when the row actually unmounts rather than on a timer, so focus never lands on `<body>`; while a rename field has focus the row order is frozen so a re-sort cannot blur it. A polite live region announces each action's outcome only when it actually succeeded (a failure toasts instead, never a false success message) and, only when a filter field changes (never on the raw session count), "Showing {x} of {n} sessions"; failures still toast through the existing `notify`. Two empty states: no sessions at all shows "No sessions yet" with a short instruction and a **Back to chat** button; a filter matching nothing shows "No matching sessions" with a **Clear filters** button.
- **Subagent panel** (spec 004 FR-017 to FR-020, FR-022): opened by the Subagents chip, lists the current turn's subagents by name/task with a state icon plus the state word (never colour alone: a spinning icon for running, a check for finished, an X for failed); selecting one shows its live stream -- text and tool calls, through the same renderers the main transcript uses -- updating within about 2 s of new output, and a finish while that stream is open updates the state in place without closing the panel. **Close** returns keyboard focus to the Subagents chip that opened it (the panel stays permanently mounted at zero width afterward, so a focused control inside it would otherwise be stranded off-screen) and leaves the chat pane exactly as it was. **Wrapping and padding** (issue #492): a long tool target, argument, or paragraph in the stream wraps within the panel's own width instead of clipping or growing the panel sideways -- fixed at the shared `ScrollArea` wrapper (`src/renderer/components/ui/scroll-area.tsx`), whose Radix `Viewport` otherwise wraps children in an internal `display: table` div sized to the widest row, so every `ScrollArea` consumer (this panel's stream, `SessionList.tsx`'s repository list) inherits the fix; `CollapsedLine`'s tool-row summary gets an opt-in `summaryWrap` prop so the chat transcript's own rows stay one-line while this narrower panel wraps instead. The header, the subagent list, and the stream all share the same `px-3`/`py-2` horizontal padding, so no row touches the panel's left or right edge.
- **Subagent panel across a split** (spec 005 convergence, research.md Decision 10): the panel stays the one shared, single instance -- a **Split**'s two **Chat panes** never each get their own. It is bound to whichever pane's Subagents chip was last activated (an explicit action); moving focus between panes alone (the focus-move chord, a row click, Ctrl+click) never silently retargets an already-open panel, the same "only an explicit action changes what it shows" rule spec 004 already established for Close/a new turn/a vanished Session.
- **Pull requests view** (spec 003, FR-001 to FR-030): a left-nav entry above the session list's repository groups (`GitPullRequestIcon`, a visible selected state while open) swaps the centre region into a **Pull requests view**, scoped to a repository chosen from a dropdown at its top (defaulting to the selected Session's repository). A list column on the left offers five filter tabs (Open, Authored by me, Assigned to me, Involves me, Review requested), a narrowing text filter, a refresh button, and a "last updated" label; each row shows title, number, check status (icon plus text, never colour alone), repository, age, and author. Selecting a row shows its detail on the right: an Overview/Changes `Tabs` pair (title, state, branches, reviewers, assignees, labels, description, and a chronological timeline of commits/comments/reviews/review threads on Overview; changed files and per-file diffs, reusing the existing `DiffView.tsx`, on Changes), a check-status header chip that polls every 15 s while a check is pending, and header actions for New session, Review, and Merge. Review/Merge/resolve each act through `src/main/github/gh.ts` (the GitHub CLI, no stored token) and refuse with an actionable reason -- `disabledReason` for a draft/closed/merged pull request, `not-mergeable` for conflicts or a failing required check, `stale` for one that changed on GitHub since it was last fetched -- rather than silently doing nothing. The spec 004 session-readout Pull request chip opens this view, pre-selected to that Session's own pull request, instead of the system browser, now that it exists.

## Chat

- **Self vs. other layout** (Stuart, 2026-10-04): your ("self") messages render as a right-aligned bubble with a left indent, so a self message never touches the transcript's left edge, paired with a right-aligned avatar; the agent's ("other") text remains full-width, left-aligned, and sits plain on the background with no bubble -- the standing layout rule for anything rendered as the user's own content versus anything from the assistant or another agent.
- **Baseline collapsed line**: every output kind that is not a user/assistant-text message builds on one shared `CollapsedLine` component (`src/renderer/features/chat/CollapsedLine.tsx`): an icon slot, a short label, a one-line summary that truncates with an ellipsis, a status/duration slot, and (when there is something to expand) a `Collapsible` expansion whose trigger is a button with `aria-expanded`. A warning or error is always a distinct icon shape, never colour alone. A new output kind starts from this component instead of growing its own one-off collapsed row; `ToolRow`, `ToolGroupRow`, the Thinking line, the answered-question row, decided approvals, the subagent, agent-message, and advisory lines, and notices/command-output all build on it.
- **Transcript rhythm** (Stuart, 2026-10-04): `MessageScrollerContent` no longer sets a uniform `gap` (`src/renderer/components/ui/message-scroller.tsx`); each row carries its own top margin instead so the rhythm between turns/real user-assistant messages (`mt-6`) and the rhythm within a run of bookkeeping rows (`mt-1`) can differ -- a nested `gap-1` sub-list was the original idea, but `MessageScrollerItem` must stay a *direct* child of `MessageScrollerContent` (`@shadcn/react/message-scroller`'s scroll-anchor/visible-message tracking enumerates only `content.children`), which rules out wrapping a run in its own flex container. Consecutive rows built on the shared `CollapsedLine` baseline -- tool-group, thinking, advisory, notice, subagent, agent-message -- get the tight `mt-1` margin between each other; everything else (a user/assistant message, an `ask` question, a request/approval card, and the first row after one of those) gets the full `mt-6` rhythm, so the chat reads as the user<->assistant exchange first and bookkeeping rows as compact, secondary material.
- **Time-gap divider** (Stuart, 2026-10-04, new): a horizontal rule showing the date and time renders as its own transcript item between two turns whenever they cross a calendar-day boundary, or sit more than an hour apart on the same day, so a resumed-the-next-day or long-running session is visible at a glance. Keyed off each turn's own `user` item timestamp; omitted when either side has no usable timestamp (same rule as the turn-total-time line).
- Each tool call is one compact row: tool, target, status, duration. Expanding shows arguments and output; a file edit shows a diff.
- **Grouped tool calls**: a run of consecutive calls to the same tool collapses to one line (status running while any call runs, failed when any failed; the last call's target plus "+ N others", ", N failed" appended in text, never colour alone); expanding shows each call as its own expandable row. A thinking line, a different tool, or a pending approval/question ends the run. `ask` calls and subagent rows are never grouped.
- **Hidden bookkeeping tools** (T086, FR-052): the agent's own tool calls for its own bookkeeping (a fixed list, `src/shared/model.ts`'s `HIDDEN_TOOLS`, starting with `todo`) never appear in the chat at all -- the only exception to "every tool call is a row". A hidden call that fails still surfaces, as a plain error notice rather than silently; that notice never splits an otherwise-consecutive run of another tool's calls apart into two groups.
- **Thinking**: a collapsed "Thinking" line shows a faint one-line preview of the latest text while it streams, and "Thought for Ns" once done; expanding shows the full text through the normal markdown path. A thinking line with no known duration (e.g. one in a reopened Conversation) shows just "Thought", never a guessed number.
- **Turn total time**: each turn's activity block ends with a muted line showing the elapsed time ("28s", "1m 14s", "2h 3m"), ticking every second while the turn runs and marked `aria-hidden` until it ends (so a screen reader only reads the final value). Omitted when no item in the turn carries usable timing (a reopened Conversation whose history has none).
- **Question formatting** (issue #491): the live question card and the answered-question expansion both render the question through the shared sanitised-markdown `Markdown` renderer at normal weight, never inside a bold title. A question with more than one line shows its first line as a short heading of medium weight, with the rest as body text with paragraph spacing, scrolling inside a maximum-height region when long so the options and Cancel are never pushed off screen; a single-line question stays one line of normal weight with no separate heading. The heading split is suppressed (whole question renders as body) when the first line starts a markdown block (fence, list item, blockquote, table row, ATX heading, thematic break, setext underline, indented code) or would leave a blank body (gate cycle 3 finding 6). A markdown hard break (two trailing spaces or a trailing backslash) in the body renders one extra blank line, a documented edge case. Options for a choice question stack vertically at full width, each with its label at medium weight and its optional description muted beneath it.
- **Answered questions**: an answered `ask` question collapses to "Asked user:" plus the question cut to one line, expanding to the full question (through the same renderer and heading/body split as the live card above) and its options, with an indented "Answer:" row below carrying a small round avatar of the user's initials, their name (`git config user.name`, falling back to the Windows account name, cached per repository), and the answer ("Cancelled" for a cancelled question). A pending question stays the live approval/question card; a decided approval keeps its own one-line resolved summary.
- **Subagents**: a batch `task()` call renders as one collapsed line per subagent it started (never grouped), each with its own status and duration, collapsed by default and expanding to its prompt and (once known) its result as plain text.
- **Agent-to-agent messages**: an IRC-style message between a subagent and the main agent (or between subagents) is its own collapsed line with a direction icon, "<sender> to <recipient>", and a one-line preview, expanding to the full message; never grouped or hidden.
- **Advisory notes** (T084/T085, FR-051): an OMP-injected `<advisory>` note (one or more per message) becomes its own baseline line, styled by severity -- a blocker in the error colour, a concern in the warning colour, a nit muted -- each also with a distinct icon shape and the severity word, since colour alone is never the cue. The advisor name and a "T-N" turns-ago marker show when present, plus a one-line preview of the note; expanding shows the full note and its guidance as plain text. A note that cannot be parsed shows as a generic notice instead of raw tag text.
- Chat text fills the full width of the transcript column; code blocks, diffs, and tables scroll sideways only when their content is wider.
- **Code blocks** (T083, FR-049/FR-050): every code block -- a fenced block in markdown, and a tool call's Arguments and Output -- shows a small header naming its language, or "text" when none is known or Shiki fails to highlight it; JSON arguments and JSON output are pretty-printed, a tool's diff-shaped output is highlighted as a diff. No copy button (FR-042).
- **Every JSON-shaped tool/code surface uses `CodeBlock`** (Stuart, 2026-10-04): the rule above has no exceptions -- a tool call's Arguments and Output, a `write` result's content preview, a subagent's Prompt and Result, and a pending approval card's detail lines are all JSON- or code-shaped and all render through the shared `CodeBlock` component (`src/renderer/features/chat/Markdown.tsx`) with language-appropriate highlighting, never as a raw, unformatted `<pre>`/`<div>` paragraph, regardless of which tool or target URI (including an `xd://` device call) produced the content.
- Sending while a turn runs queues a removable chip under the turn; "Send now" on the chip steers the running turn.
- Approval requests and agent questions appear inline in the transcript at the point they arise, with Approve / Deny or the answer controls, and mark the Session as needs you.
- **Split chat pane** (spec 005): each pane is a complete, independently-scoped chat for its own Session -- header, transcript, message box, queued messages, pending approvals/questions, and the readout chip row -- matching what a single, unsplit pane shows for that Session; a pending approval or question in the unfocused pane stays visible and answerable there without focusing it first. Both panes keep streaming live at the same time; activity in one never delays typing or streaming in the other.
- Agent text, tool output, and file contents are always shown as inert content.
- **GitHub-flavoured markdown** (tables, task lists, strikethrough, footnotes) renders on every markdown surface (assistant text, user text, the Thinking row): tables sit in a horizontally-scrolling wrapper with bordered header/data cells; task-list checkboxes are disabled, themed checkboxes; footnotes land in a divided section at the end of the message, numbered and back-linked. Raw HTML in agent/user text never renders (constitution V): it is sanitised away or shown as plain text, never as live markup.
- **Mermaid diagrams** (a ```` ```mermaid ```` fence) render as an inert image, never inline SVG: Mermaid itself (`securityLevel: 'strict'`) is loaded only once the first diagram actually appears, and the rendered SVG is shown as a `data:image/svg+xml` `<img>` -- browsers disable script execution for SVG used as an image, so a diagram cannot run code regardless of what its source contains. A diagram still streaming, over a 50 KB source cap, past a 5 s render timeout, or that fails to parse falls back to the fenced source with a one-line reason above it, never a blank area. Every rendered diagram has a **Show source** toggle and an `aria-label` naming its Mermaid diagram type.
- **Message box** (T063): a solid field, darker than the page background (never a translucent alpha composite -- see "Composer tone" below), with a subtle border and a `focus-within` ring replacing the text area's own. Send and Stop are round, icon-only, outline-styled buttons (accessible names "Send message"/"Stop", no visible label text) vertically centered on the field's right edge so they stay centered as the textarea grows to multiple lines, rather than pinned to a corner; Send shows an up-arrow icon, Stop a square icon, both the exact same size/weight. Each shows its shortcut as key-cap icons (the `Kbd` component) in its tooltip on hover and keyboard focus -- Send: **Enter**, Stop: **Ctrl**+**Shift**+**X**. A muted readout along the bottom of the field shows the Session's provider, model name, and reasoning effort (T062's `lastModel`/`lastThinkingLevel`, the last known values even when the agent is not running), reading "Model not known yet" before any Session has ever reported one.
- **Composer tone** (Stuart, 2026-10-04): the message box's fill reads as visually recessive against the page: strictly darker than `--background`, never an alpha composite of `--background` (or of a lighter token such as `--muted`, `--secondary`, `--accent`, or `--card`, all of which sit lighter than `--background` in the dark theme) layered over itself, which is a no-op. The composer must never compete visually with the transcript above it.
- **Ghost-text word completion** (T103, FR-058): while typing a prose word at the end of a line in the message box, a short debounce after the last keystroke shows its likely completion as dimmed, non-selectable inline text right after the cursor -- an overlay, never part of the textarea's own value or selection. Trigger is local-only and never fires mid-word, inside a file-path-shaped token, or inside a slash command. **Tab** accepts the shown suggestion, inserting exactly its text and moving the cursor past it (Tab with nothing shown keeps its normal field-leaving focus movement); **Esc**, typing past it, or any other edit dismisses it. Each shown-then-resolved suggestion reports back to OMP whether it was accepted or abandoned. The request only ever reaches an already-running agent process -- never one that would have to start first -- so typing in a stopped Session's composer never launches its agent (a cold shared prediction daemon's first call can take up to about two minutes). A failed or unavailable prediction degrades silently to no suggestion, never a toast or any other visible error. A screen-reader-only live region (referenced from the field's `aria-describedby`) announces when a suggestion becomes available, without firing on every keystroke.
- **Pasted image attachments** (spec 009, FR-001 to FR-009, FR-018, FR-019): pasting an image into the message box creates a pending thumbnail in a shared attachment strip directly above the box (hidden entirely while nothing is pending) instead of inserting any image data into the textarea's own text; clicking a thumbnail opens the full image in a modal, Esc or an outside click closing it and returning focus to the thumbnail. A pasted image not already PNG/JPEG/GIF/WebP is re-encoded to PNG in the renderer before it ever becomes a pending attachment (Refract never relies on OMP's own fallback); a decoded image over 20 MiB is rejected with an inline toast naming the limit, never shrunk, never sent. Several images may be pending at once, each with its own thumbnail and remove control, independent of each other and of any pending text chip. Sending includes every pending image as a real `images` entry (base64 + mime type) on the `prompt`/`steer` command, clearing the strip once that send is accepted -- not once the agent's turn finishes, so the composer's ordinary sending/working indication carries through OMP's own extra vision-description delay (up to 20 s) without ever looking stalled or showing an error. The main process re-validates every image's mime type and decoded size independently before it is ever sent (constitution Principle V): the renderer's own paste-time check is never trusted alone.
- **Pasted text chips** (spec 009, FR-010 to FR-015): pasting a block of plain text over 800 characters collapses it into a short labelled chip ("first line truncated… (N chars)") right at the position it was pasted, instead of flooding the textarea with the raw block; at or under that threshold a paste still lands exactly as before. The chip's clickable surface renders twice, deliberately: once as a badge in the shared attachment strip (always reachable regardless of the textarea's own scroll position) and once as an inline overlay positioned exactly over the chip's own label text in the draft, reusing the ghost-text overlay's text-metrics technique (T103, FR-058) so it looks and clicks like a chip sitting in place rather than plain text -- both open the same read-only, scrollable text modal. A chip is dropped from pending state the moment its label no longer appears intact in the draft (an edit or an ordinary delete both count), silently and without error; several chips may be pending in one draft at once. Sending substitutes every still-pending chip's full original text back into the plain message string at its own position, independently of the others -- OMP only ever sees the plain string it would have gotten pasting the whole block directly, no new wire capability involved.
- **Draft persistence** (spec 010, FR-001 to FR-005): the message box's in-progress text and its pending attachments (both bullets above) survive switching the visible Session away and back, and opening Settings and returning to chat -- the two things that unmount and remount the message box's own component -- restored exactly as left, cursor at the end of the text, each open Session tracked independently so switching never shows or mixes one Session's draft with another's. Sending still clears both immediately, exactly as before. Renderer-memory only, same as everything above it: a restart loses it exactly as it always has.
- **Slash commands** (FR-032, FR-033): typing `/` lists only the commands Refract has actually verified work end to end on the supported OMP version, from a fixed supported set in `src/shared/slash-commands.ts` -- never OMP's raw, unfiltered list. A command OMP offers that is destructive-shaped, config/credential-shaped, terminal-only, or simply not yet probed is left out of the menu entirely, not shown disabled; typing one by hand gets the same unknown-command warning as a name OMP has never heard of, and nothing is sent. Every listed command is run to a visible result: its own `command_output` line, a notice on failure, or the dialog it raises answered through the ordinary request cards -- never a silent no-op. Adding a command after a newer OMP patch: rerun `docs/spike/slash-commands-probe.mjs` (constitution IV), record the result in `docs/spike/FINDINGS.md` and `contracts/omp-usage.md`, then add the name to `SUPPORTED_OMP_COMMANDS`; a command whose own result Refract cannot yet show (a new dialog/output shape) gets that support built first, or stays out of the set until it does.

## Confirmed in implementation

- **Opening a Session** (spec 005: generalised from a singleton to `split-store.ts`'s per-pane targeting): a plain row click that is not already shown anywhere calls `replaceFocused`, which clears the id's pristine flag and (for a changed `sessionId`) lets that pane's own `ChatPane` effect ask for a snapshot (`sessions.open`) and apply it (transcript, queue, pending requests, stop banner); a row already shown in the unfocused pane just moves focus there instead of duplicating it. Clicking the row for the session already shown in the FOCUSED pane (waking a `not-started` or otherwise-stopped Session) calls `open` directly as well, since no `sessionId` change would otherwise trigger that pane's effect.
- **Approval mode switch**: changing the pill's mode persists immediately, but a live Session only restarts into it once it is idle with nothing pending (`pendingMode` on the runtime view); the pill itself shows "<mode> after this turn" while a restart is pending (spec 001 T098 moved this off the chat header). A Session that is not live simply launches in the new mode next time.
- **Reattaching a live process to a Conversation** (`switch_session`, used by both session-open and the mode-change restart) is verified, not assumed: after the RPC call reports `cancelled: false`, Refract calls `get_state` and checks its `sessionFile` matches and `messageCount` is greater than 0; a `messageCount` lower than the Conversation's last known `lastMessageCount` is not itself a failure (FINDINGS item 44) -- OMP can drop messages (at least aborted assistant turns) on reload, so Refract re-baselines `lastMessageCount` to the observed value and shows a one-time notice instead of failing. A failed check (`sessionFile` mismatch or a zero count) rolls back to the previous Conversation where possible.
- **Readiness ("OMP signed in")**: `get_state`'s current model must also appear in `get_available_models`; a resolved `{provider, id}` from `get_state` alone is not diagnostic of sign-in (disabled or uncredentialled providers can still show up there), so the model-presence check is the actual signal. `get_login_providers` is used only to enrich the failure hint with the unauthenticated provider ids.
- **Tool rows**: a `write` result shows "Wrote N lines to `<path>`"; an `edit` result shows a diff built from the tool's own `details.oldText`/`details.newText` (not a general-purpose git diff, which is unreliable per-call once several edits touch the same file in one turn).
- **Session list keyboard and focus model**: each row is one button (open/wake) plus an `⋮` menu trigger (rename, archive/restore, stop agent, delete), and the same actions are also reachable by right-clicking anywhere on the row (a `ContextMenu`, one action list shared with the `⋮` dropdown so the two menus never drift apart) or via the row's native context-menu keys (`Shift+F10`, the Menu key) once the row has focus. F2 on the focused row button starts renaming; Enter/Escape commit or cancel it. Archive/restore/delete can unmount the focused row (sometimes its whole group), so every such action captures a fallback chain before acting -- next row, then previous row, then the Repository's own collapsible trigger, then the Sessions nav root -- so focus never lands on `<body>` (WCAG 2.1 AA).
- **Motion**: a `prefers-reduced-motion: reduce` media query disables animation globally (spinners, transitions), leaving colour, icon, and `sr-only` state text as the non-motion signal.
- **State icons**: each Session state (`working`, `idle`, `needs-you`, `stopped`) pairs a distinct icon and colour with an `sr-only` text label (`STATUS_LABEL`), so colour is never the only signal, including for screen readers. `idle`, `needs-you`, and `stopped` use a Lucide icon; `working` instead uses the animating brand mark (`BrandSpinner`, spec 011) -- still a distinct, decorative icon with the same `sr-only` label, just not a Lucide one.
- **Last known model freshness** (T062): `sessions.list()` computes `SessionSummary` fresh from the registry on every call, but the renderer's own cached `sessions` array is only refreshed on `session:list-changed`, not on every `get_state`. `sessions.open`/`sessions.recover` emit it once a start actually ran, so the message box and details card readouts reflect a just-started Session's model without waiting for an unrelated rename/archive/restore to trigger the next refresh.
