## Selection rule result
Rule 1 (prefer rpc-ui if C1, C3, C4-or-C18, C8, C9 pass and C7 works): C1 PASS, C3 PASS, C18 PASS (C4 native FAIL, fallback works), C8 PASS, C9 PASS, C7 core ops PASS (`branch` unresolved). **Selected transport: `omp --mode rpc-ui`, one process per session/worktree, full-feature launch.**

Why not the others:
- ACP: session ids do not survive process restart (C16), so the session list/switcher cannot reattach after an app relaunch; `/btw`, `/plan`, `/fork`, `/resume`, `/new`, `/settings` are also missing; `ask` turn cancelled unexpectedly. Its wins: multi-session per process, native permission/elicitation forms, fs write bridge for diff preview.
- SDK: cannot surface tool-approval prompts at all (C21, `createAgentSession` never calls `ExtensionRunner.initialize`), `ask` crashes with a stub UI, no subagent events, and needs a Bun sidecar because Node cannot import it. Its win: no per-session process spawn, faster warm start.

## Consequences for the desktop app (chosen transport: rpc-ui)
1. **Commands the UI must supply natively or drop** (absent over RPC): `/plan`, `/fork`, `/resume`, `/new`, `/settings`, `/pause`, `/plan-review`, `/btw`. `/new` and `/resume` map to `new_session` and `switch_session`/`open_session`. `/btw` maps to an extension command built on `ctx.runEphemeralTurn` (proven, C18); the app should ship that extension and NOT forward literal `/btw ...` (it silently becomes a normal, persisted turn).
2. **Available over RPC and worth surfacing:** `/model /compact /handoff /move /marketplace /reload-plugins /todo /usage /context /mcp /jobs /session /wt /add-dir /dirs`, plus 175 `skill:*` commands and extension/custom/file commands. `/wt` (a built-in) may cover worktree operations: unverified, test before designing worktree creation UI around it.
3. **Dialog handling:** both approvals and `ask` arrive as generic `select` requests. The UI must tell them apart by title prefix `Allow tool:` versus everything else, and `ask` loses headers, previews, notes, and images over RPC.
4. **Host gotchas seen live:**
   - Prompt payload field is `message`. `text` is silently accepted and returns `success:false` with an opaque TypeError.
   - Local-only slash commands (`agentInvoked:false`) emit no `prompt_result`; `command_output` can arrive before or after the ack.
   - After `abort`, wait for `session_settled` before sending another prompt, else "Agent is already processing".
   - Unknown `/foo` text is not rejected; it goes to the model as a normal prompt.
   - `branch` needs an entry id contract that was not resolved.
5. **Left pane:** RPC has no list-sessions command in the frames observed; list sessions by scanning JSONL files in the session dir and reattach with `--resume <sessionFile>` at spawn, `switch_session {sessionPath}`, or `open_session {sessionDir}` (all passed C16). Confirmed by the probe:
   - `switch_session` to a missing path returns `success: true, cancelled: false` and starts an empty session (`messageCount: 0`), so confirm every reattach with `get_state` `sessionFile` and `messageCount`.
   - Spawning `omp --mode rpc-ui --session-dir <dir>`, and attaching by any of the three routes, creates no new `*.jsonl` file; the session file is created lazily, so scanning the dir does not accumulate empty entries. (The one exception is the missing-path `switch_session` above, which creates a file at that exact path.)
   - `open_session {sessionDir}` picks the newest non-empty session even when a newer empty one exists.
   - The process cwd must be the session's own worktree. `switch_session` to a session recorded under a different cwd returned `success: true, cancelled: true` and left the process on a fresh empty session (`messageCount: 0`), so spawn each session's process with that worktree as its cwd.
   - OMP rewrites the session file on reopen, so byte size can shrink (one run: 36292 -> 25972 bytes). The only difference found is that `providerPayload` (provider-side replay state, ~5-6 KB per assistant entry) is dropped; visible text and tool calls are byte-identical. The recall check shows the conversation still continues, but the provider's hidden reasoning chain does not carry across a reopen, and the first turn after it may lose prompt-cache hits. Do not detect changes by file size; count entries.
   Kill process trees with `taskkill /PID <pid> /T /F`.
6. **Cold start:** measured 2026-09-30 by `memory-probe.mjs`, 3 sequential runs: spawn to `ready` 2.2 to 3.9 s; `ready` to first answer token 11.7 to 15.3 s; full tiny turn 17.7 to 22.5 s. Measured with about 12 unrelated `omp` processes running on the machine, so it is not an idle-machine number. Spawning a process per Session ahead of use costs about 1.1 to 1.7 GB each (item 13), so Pinion starts a Session's agent when the Session is opened.
7. **Config note:** the test machine's global `tools.approvalMode` was yolo; an app that wants an approval UI must pass `--approval-mode=always-ask` explicitly.
8. **Bun requirement:** rpc-ui needs no Bun in the app (child process over stdio); only the SDK path would.
9. **Approval mode is launch-only:** OMP's `rpc.md` documents no command to change `tools.approvalMode` on a live process, so a change reaches a running session only through a process restart plus reattach (C16). `omp://approval-mode.md`: modes are `always-ask` (auto-approves `read`, prompts `write` and `exec`), `write` (prompts `exec` only), and `yolo`; per-tool `tools.approval.<tool>: allow|deny|prompt` user overrides apply in every mode, so `yolo` can still prompt; subagents run headless in `yolo`. Read from the docs, not probed.
10. **Parent death (Windows):** when the parent was killed with `taskkill /F` (no `/T`), `omp` and its own MCP-server children exited within about 6 s, but a tool subprocess survived: `ping.exe -n 120` (started by the `bash` tool) was still running 30 s later and had to be killed by hand (`orphan-probe.mjs`, 2026-09-30, descendant tree walked by parent pid). Reaping recorded `omp` pids at next start cannot find such subprocesses. See item 12 for the fix.
11. **Session directory:** without `--session-dir`, OMP writes each cwd's Conversations to its own directory under `~/.omp/agent/sessions/`, one per worktree; two worktrees of one repository get different directories (`session-dir-probe.mjs`, 2026-09-30). `--resume <file>` and `open_session {sessionDir}` both restore history when the process cwd matches; a bare relaunch does not continue anything; the file is created lazily on the first message. `switch_session` from a process with a different cwd returns `cancelled: true`. The file name starts with an ISO timestamp (created time without opening the file); line 1 is a `title` slot; the first user message is within the first 8 KB. The directory name's encoding is not needed by Pinion: take `dirname(sessionFile)` from `get_state` once. Observed on Windows with a cwd under `%TEMP%` (which is inside the user profile): the name is `-` plus the home-relative path with separators as dashes; `session.md`'s temp-dir rule did not apply.
12. **Job Object stops the whole tree:** a Windows Job Object with `KILL_ON_JOB_CLOSE`, created through the `koffi` npm package (prebuilt binary, no native compile), killed the whole `omp` tree when the parent was force-killed (`job-object-probe.mjs`, 2026-09-30). Best variant, **self-join**: the parent assigns itself to the job before spawning `omp`, so every descendant inherits membership at creation. With omp driving a real `bash` tool, all 19 to 20 descendants (workers, four MCP servers with nested node/uvx/cmd/python children, `ping.exe`, conhosts) were gone within 1 s, zero escapees, both plain and when the parent was itself started inside another job (nested jobs work). The same self-join code also ran inside Electron 44.5.1's main process with `koffi` and killed a child when the Electron main was force-killed. Assign-after-spawn (`omp` pid assigned 38 to 53 ms after `spawn`) also killed everything, but a child that already existed (a conhost) escaped the job in 2 of 3 runs and only died by console lifecycle; assigning 1.5 s late is unsafe. Use self-join. Not tested: a packaged Electron build (native `koffi` binary must be unpacked from asar). **T004, confirmed in the real app (2026-09-30):** the same self-join code (`CreateJobObjectW` + `SetInformationJobObject` with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` at offset 16 + `AssignProcessToJobObject(job, GetCurrentProcess())`), run from `src/main/index.ts` of the actual `pnpm build` output (not a throwaway project) with `koffi` 3.3.2, spawned `ping -n 120 127.0.0.1` as a real child (`PING.EXE`, with its own nested `conhost.exe`); force-killing only the main `electron.exe` pid (`taskkill /PID <pid> /F`, no `/T`) left both the ping process and its conhost grandchild gone, confirmed within the 5 s window. **`shell.openExternal` side effect (issue #68, 2026-10-02):** with Firefox (MSIX package, the default `https` handler, started through `DelegateExecute`) fully closed, a link opened from an isolated built Refract instance (`open-external-probe.mjs`, Electron spawned detached, out of Node's own spawn job) cold-started Firefox, and all of Firefox's processes survived a force-kill of the Electron main pid. The run's controls all held: the main process joined the job (no `joinKillOnCloseJob failed`, with a logged control proving its console was captured), Electron really exited, and Firefox served the probe URL. Firefox's root process had a parent other than Electron (pid 3544, already exited when the processes were listed after the hit). Refract's job allows no breakaway, so Firefox surviving means it was never in that job; that the AppX activation broker started it is [INFERENCE]. The URL arrived intact (comma, `%20`, and a literal `%USERNAME%` not expanded). Not tested: an unpackaged default browser (Chrome, or Edge as default), which Windows would likely start as Refract's own child [INFERENCE].
13. **Memory:** a live Session (one `omp` plus its tool servers, about 24 processes with the tested user config) held about 1.15 GB working set idle and about 1.9 GB while answering; two idle Sessions 2.9 GB and three 3.9 GB; the marginal cost per extra idle Session was noisy, 1.0 to 1.7 GB (`memory-probe.mjs`, 2026-09-30). Free physical memory fell to 292 MB during the mid-turn sample on the 16 GB test machine, which also hosted about 12 unrelated `omp` processes. Most of the cost is the user's own MCP servers, not the agent.
14. **Edit/write tool result shapes (diff source):** `tool_execution_end` `result.details` for `edit` carries the full `oldText` and `newText` (whole-file before/after text) plus a compact non-unified `diff` summary string (`" N|line\n-N|old\n+N|new"`); no unified-diff markers (`@@`, `---`, `+++`) appear anywhere in the captured frames. `write` carries only `resolvedPath` in `details`, no old content, so Pinion must supply the "old" side itself from a per-path last-known-content cache seeded by earlier `read`/`edit` results observed in the session (empty cache entry = new-file diff). `edit` requires a snapshot tag obtained from a prior `read` of the same path in the same session: calling it cold fails with `Missing hashline snapshot tag for <path>; use "[<path>#tag]" ...` (`isError:true`, empty `details`). `git diff` in the worktree after the call is not a reliable per-call fallback: it is cumulative since the last commit, so it cannot be attributed to one call when several calls touch the same file in a turn, or when the target sits outside or is ignored by a git repo (`edit-diff-probe.mjs`, 2026-09-30).
15. **"OMP signed in" readiness signal:** `get_state.model` is present with a resolved `{provider, id}` even with zero stored credentials, so it is NOT diagnostic of sign-in. `get_available_models` already filters to models from authenticated, non-disabled providers (`model-resolver.ts`: "so disabled providers and providers without credentials are already filtered out") — it read 67 (one authenticated provider) on the real signed-in machine and 0 on a freshly-created, never-used `--profile pinion-probe-empty` process with every credential-shaped env var stripped, but it is only a corroborating signal because it is also scoped by the `enabledModels` config pattern. `get_login_providers` is the direct, purpose-built signal: `data.providers[].authenticated` ref…. The rule Pinion ships is: `ompSignedIn` is ok iff `get_available_models` contains an entry matching `get_state.model`'s `{provider, id}`, because that checks the default model can actually run; `get_login_providers` is used only to enrich the failure hint, never as the primary check.
16. **Job Object kill-on-close covers a mid-turn tool subprocess, and `reapStale()` reaps a genuinely still-running orphan (T035, 2026-09-30):** repeated the force-kill guarantee from item 12 with a Session actually mid-turn: the built app (`out/main/index.js`, `--user-data-dir` pointed at a scratch profile) opened a seeded Session and `chat.send` asked the agent to run `ping -n 120 127.0.0.1` via the `bash` tool under `--approval-mode=yolo` (no approval gate in the way). With the descendant tree confirmed live via `Get-CimInstance Win32_Process` (`ParentProcessId` walked from the Electron main pid): the main process itself, its own `gpu-process`/`renderer`/`utility` helpers, the spawned `omp.exe`, omp's own `mnemopi_embed` worker, and `ping.exe` (7 processes). A single `Stop-Process -Force` on ONLY the Electron main pid (no process-tree flag, matching Task Manager's "End task") cleared all 7 within 1 s of polling (`Win32_Process` once per second), well inside the 10 s budget. A second, unrelated Pinion instance running under a different `--user-data-dir` on the same machine was unaffected. Separately, `reapStale()` was proven against a real still-running process rather than a synthetic record: a bare `omp --mode rpc-ui` spawned outside Pinion had its pid, `StartTime`, and image name (queried the same way `recordProcess` does) written into a fresh `processes.json`; starting a new Pinion instance against that `--user-data-dir` `taskkill`ed it and rewrote `processes.json` to `[]` within the first few seconds of `app.whenReady()`, before any window opened.
17. **`--resume` is unsafe after a worktree is recreated; use `switch_session` (2026-09-30):** a Session's worktree was removed with `git worktree remove --force` and recreated at the identical path (branch kept). A fresh `omp --mode rpc-ui` started with `--resume <sessionFile>` (same cwd string, same cwd recorded inside the file) reported `messageCount: 0`, and when that process exited it overwrote the file with a blank session at the same file name. `switch_session` with the same file, process, and cwd at the same moment correctly reported the full history. Root cause inside OMP was not isolated. Pinion therefore binds every reattach with `switch_session` and never passes `--resume` (constitution Principle III, v1.5.0). Also observed: `get_state` returns a `sessionFile` before any message exists (the file is created lazily), so Pinion records `currentConversation` and `lastMessageCount` only once `messageCount > 0`.
18. **End-to-end run on the built app (2026-09-30):** with a scratch repository, real `omp` 18.4.4 and an isolated user-data directory, driven over the Chrome DevTools Protocol: readiness, add repository, create Session (worktree on disk), open, chat, an Ask-mode `write` approval (approve wrote the file, deny did not), stop and reopen an agent, `/new` and reopen an earlier Conversation, archive and restore, `deleteCheck`, missing worktree then recreate, confirmed delete (worktree, branch, and Conversation files gone), force-kill of the Electron main (all 21 descendants gone, stale pid record cleared at relaunch), relaunch with history restored and a recall question answered from before the kill, unread marking for a hidden Session, and crash recovery. Defects found and fixed along the way are in the commit history.
19. **omp 18.4.5 re-probe (2026-09-30):** the box upgraded to `omp` 18.4.5, so the three probes Pinion's contracts rely on were rerun there. `resume-probe.mjs`: every check PASS (attach by `switch_session`, `open_session`, `--resume` on the original file in the ordinary case; history, continuation, append, and persistence all match; `open_session` still skips a newer empty session). `signed-in-probe.mjs`: the signed-in profile returns 67 models and two authenticated providers (`authenticatedCount: 2`); the empty `--profile pinion-probe-empty` process returns 0 models and 0 authenticated providers, still reports a `get_state.model`, and a prompt fails with "No API key found", so the readiness rule (`get_state.model` contained in `get_available_models`) discriminates on 18.4.5. `edit-diff-probe.mjs`: `edit` results still carry `details.oldText` and `details.newText`; `write` results still carry only `details.resolvedPath` and the text `Successfully wrote N bytes`. No FINDINGS row Pinion relies on changed, so the supported range is 18.4.x (constitution 1.6.0).
20. **A Conversation can gain messages outside the settle flow (2026-10-01, omp 18.4.5):** during a quickstart run on the built app, a Session was stopped and reopened, and reattach verification failed because the fresh process reported a higher `messageCount` than Pinion's last known one (the run's report gave 11 against 10). The reporting subagent's `get_state`/`get_messages` dump showed one extra `<advisory>` message that no turn or `session_settled` produced. The dump was not saved, so this row is an observation relayed from that run, not a reproducible probe, and the cause (the child `omp` loading the user's own `~/.omp/agent` advisor or hooks) is inferred, not isolated. The consequence does not depend on the cause: any message appended outside the settle flow makes an exact-equality check fail a healthy Session after Stop or Recover. Pinion therefore requires `messageCount` to be non-zero and not below the saved count (constitution Principle III v1.7.0, data-model.md "Reattach verification"). To confirm: resume a Session, append a message through the omp CLI outside Pinion, and reattach.
21. **No model-role source over RPC (T061, 2026-10-02, omp 18.4.10):** `model-role-probe.mjs` sent four read-only RPC requests (`get_state`, `get_available_models`, `get_available_thinking_levels`, `get_available_commands`) against the real signed-in profile and regex-scanned every key and string value for `role|profile|tier|alias|purpose`. No `role`/`modelRole`/`roleId` field exists anywhere in the read-only RPC surface: `get_state.model` carries only provider/id, `get_available_models` entries carry capability/cost metadata with no role/tier/alias field, and the only matches were slash-command `aliases` (unrelated) and an OpenAI-specific `compat.supportsDeveloperRole` request-shaping flag. `omp://models.md` documents config-side **model roles** (`modelRoles` in `config.yml`: `default`, `smol`, `slow`, `vision`, `plan`, `commit`, `tiny`, `task`, `advisor`, plus memory-kind roles) used to pick which model answers a request, but this is a config/selection mechanism, never reported back over RPC for the live session; `omp://rpc.md` does not mention model roles at all. Consequence: the message-box readout shows provider, model, and effort/thinking-level only; there is no role to display alongside them.
22. **Chat-line wire shapes for ask/todo/subagent (T071, 2026-10-02, omp 18.4.10):** `chat-lines-probe.mjs` ran six scenarios against the real signed-in profile (scratch `--session-dir`, every tool approval denied except the `task` tool's own gate, which was deliberately approved so the batch-subagent scenarios could run — meaning any tool call a spawned subagent itself made executed with no approval gate at all, under the real profile's real credentials). (a) A multiple-choice `ask` is a plain `extension_ui_request` (`method: "select"`) whose answer surfaces only in the resulting `toolResult` (`content[0].text = "User selected: A"`, `details = {question, options, multi, selectedOptions}`) — no separate answer event, so a transcript renderer needs no correlation with the dialog frame. (b) Free-text `ask` is two dialogs in sequence (a `select` offering "Other (type your own)", then a `method: "editor"` dialog for the actual text); the finished answer is still read from `toolResult.details.customInput`. (c) A cancelled `ask` returns `isError: true`, a fixed sentence, and an empty `details` (no `question`/`options`), so a renderer must special-case that shape. (d) `todo` tool calls carry `details.phases` per call; `get_state().todoPhases` mirrors the same `{name, tasks:[{content, status}]}` shape as live session state, independent of any one call. (e) A batch `task()` call's own `tool_execution_end` completes almost immediately with `details.progress[]` (per-subagent `id`/`status`, stuck at `"pending"`); real completion arrives later as a separate `custom`/`async-result` message whose `details.jobs[]` (`jobId`/`label`/`durationMs`/`schema.data`) is the authoritative per-subagent result — `agent_start`/`agent_end` frames carry no subagent id and cannot be correlated. `set_subagent_subscription` does not exist in `get_available_commands` on 18.4.10. (f) A subagent explicitly asked to send an IRC-style message to its parent instead just reported back that it "sent" one; no `write agent://`-shaped frame was observed within the probe's timeout — left open for a future probe with a longer timeout or narrower prompt.
