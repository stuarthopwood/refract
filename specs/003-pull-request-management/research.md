# Research: Pull request management

Each decision below resolves one open design question or one "NEEDS CLARIFICATION" from plan.md's Technical Context. Decisions 3 to 6 and the polling-interval decision originally depended on a `gh` CLI or GitHub API fact not yet checked against this machine's installed `gh` version; Phase 1's five probe tasks (T001 to T005 in tasks.md) ran live on 2026-10-04 against the real `stuarthopwood/refract` repository and resolved every one of them — each decision below is now marked **CONFIRMED** with a citation into `docs/spike/FINDINGS.md`, per constitution Principle IV.

## Decisions

### 1. GitHub access: `gh` CLI only, no stored token

- **Decision**: every GitHub read and write shells out to the developer's already-signed-in GitHub CLI (`gh`) from the main process, with `cwd` set to the repository's path so `gh` auto-detects the remote exactly as `gh pr list` does interactively. Refract stores no token, cookie, or credential of its own (FR-027).
- **Rationale**: this is the same stance the constitution already takes for `omp` (Principle I: Refract is a host, not a credential store) and the one spec 008 (profile and accounts) is designed around: "the GitHub CLI does the sign-in... a spike on a Refract-owned GitHub OAuth flow is a separate later task." Building a second, parallel OAuth flow for this spec would contradict that decision before spec 008 lands.
- **Active account, until spec 008 lands**: spec 003's own line says "Access to GitHub is the active GitHub account of the profile menu (spec 008)," but spec 008 is still Draft and its account switcher does not exist in the code yet. Until it does, this feature uses whichever account `gh auth status` reports as currently active — there is exactly one "active" account from `gh`'s own point of view today. When spec 008's `gh auth switch` wiring lands, it changes which account is active before Refract's next `gh` call; this feature needs no change for that to work, because it never caches which account answered a request, only the request's own result.
- **Alternatives considered**: a Refract-owned OAuth device flow (rejected: spec 008 already assigns this to a later, separate spike, and duplicating it here would pre-empt that decision); the Octokit REST/GraphQL client authenticated with a token read from `gh`'s own credential store (rejected: reads a token into Refract's process after all, which is exactly what FR-027 forbids — `gh` must run the request itself, not merely supply a secret for Refract to use directly).

### 2. No separate readiness gate for GitHub

- **Decision**: unlike `git`/`omp`/sign-in (spec 001's blocking readiness checklist), "GitHub access is not available" is handled entirely inside the Pull requests view itself (FR-026), not as a new blocking screen before the app is usable.
- **Rationale**: a developer who never opens a repository's Pull requests view should never be blocked by a GitHub check; spec 001's readiness screen exists because every Session depends on `git` and `omp`, but no Session depends on GitHub. The spec's own wording ("the view MUST show an actionable message instead of an empty or broken list") scopes the failure to the view.

### 3. Porcelain `gh` commands plus `gh api graphql` for what porcelain doesn't expose — **CONFIRMED by probes T001 to T003, 2026-10-04 (`docs/spike/FINDINGS.md` rows 37 to 39)**

- **Decision**: list and view data come from `gh pr list --json <fields>` and `gh pr view <number> --json <fields>` (and `gh search prs "<qualifier>"` for the four non-Open filter tabs, per T001). Review-thread resolution state, in-thread replies, and a true chronological timeline come from `gh api graphql` with a hand-written query/mutations (`reviewThreads`, `timelineItems`, `resolveReviewThread`, `unresolveReviewThread`, `addPullRequestReviewComment(input: { inReplyTo: ... })`), because `gh pr view --json` has no field for thread resolution or a unified timeline (T002, T003).
- **Rationale**: `gh`'s porcelain commands cover the common, flat fields (title, state, branches, labels, mergeable, statusCheckRollup) with a stable, documented `--json` surface; the GitHub REST/GraphQL fields this spec also needs (thread resolution, in-reply-to comments, a mixed-type timeline) only exist in the GraphQL schema, and `gh api graphql` is the sanctioned way to reach it without a separate HTTP client or stored token (it rides `gh`'s own authentication).
- **What the probes confirmed**:
  - T001 (`docs/spike/gh-pr-list-probe.mjs`): `gh pr list --json number,title,state,isDraft,author,headRefName,baseRefName,updatedAt,statusCheckRollup,labels,reviewRequests,assignees` round-trips every field name unchanged against `stuarthopwood/refract`'s 4 real PRs. All four filter-tab qualifiers (`author:@me`, `assignee:@me`, `involves:@me`, `review-requested:@me`) run via `gh search prs --repo <repo> "<qualifier>"` without error; only `involves:@me` matched real data on this account/repo (the other three legitimately returned 0, since the real PRs are dependabot-authored with no human author/assignee/reviewer). `gh search prs --help`'s own `--json` field list is a different, narrower set (`assignees, author, authorAssociation, body, closedAt, commentsCount, createdAt, id, isDraft, isLocked, isPullRequest, labels, number, repository, state, title, updatedAt, url`) than `gh pr list --json`'s — a client must map onto two distinct field sets depending on which tab is active, not one shared one.
  - T002 (`docs/spike/gh-pr-view-probe.mjs`): `gh pr view --json` covering Overview, mergeability (`mergeable`, `mergeStateStatus`), and changed files (`files: {path, additions, deletions, changeType}`) confirmed live on PR #95 and #96. The porcelain `files` field **never** carries a `patch` key, not even for a tiny one-line diff; `patch` is only reachable via `gh api repos/<owner>/<repo>/pulls/<n>/files` (REST), confirmed live on the same two PRs (feeds decision 5's revised `string | undefined` shape).
  - T003 (`docs/spike/gh-pr-graphql-probe.mjs`): the `reviewThreads`/`timelineItems` connection shapes and all three mutation input shapes (`ResolveReviewThreadInput`, `UnresolveReviewThreadInput`, `AddPullRequestReviewCommentInput`) confirmed live, the latter via GraphQL `__type` introspection only — no mutation was ever executed, per an explicit safety steer during the probe session. `inReplyTo` is confirmed as a real, current `AddPullRequestReviewCommentInput` field. No automated (Copilot) review exists on any of this repo's real PRs, so the finding-severity *representation* (decision 4) is confirmed negative for a dedicated schema field, but its comment-body convention remains unconfirmed by a live sample.
- **Alternatives considered**: calling the GitHub REST/GraphQL API directly with `fetch` and a token read out of `gh`'s credential file (rejected: same FR-027 problem as decision 1 — `gh` itself must be the thing that authenticates, not merely a token source); using only `gh pr view --json` and reconstructing a timeline from its separate `comments`/`reviews`/`commits` arrays without GraphQL (rejected for review threads specifically, because resolution state and in-reply-to linkage are GraphQL-only; accepted as a fallback decision for the timeline items that porcelain *does* cover, see decision shape in data-model.md).

### 4. Automated-reviewer findings and severity — **CONFIRMED NEGATIVE for a dedicated field; comment-body convention still unconfirmed, probe T003, 2026-10-04 (`docs/spike/FINDINGS.md` row 39)**

- **Decision**: `AutomatedFinding.severity` is typed as `'low' | 'medium' | 'high' | 'critical' | 'unknown'`, with `'unknown'` as the default: both because the probe confirms no structured severity field exists anywhere near a review thread or comment, and because no automated (Copilot) review exists on any real pull request in the probed repo, so the free-text comment-body convention itself was never observed live. The spec only requires that a finding's severity be shown (FR-008); it does not fix the value set (checklist CHK024), so this is a design-time decision made here, not a spec change.
- **Rationale**: T003's live `__type` introspection of `PullRequestReviewThread` (19 fields) and `PullRequestReviewComment` (44 fields) against the real, current GitHub GraphQL schema found no field name matching `/severity/i` on either type, nor on the 81-value `PullRequestTimelineItemsItemType` enum — confirming GitHub's Copilot code-review severity is not a stable GraphQL field, not merely undocumented. Shipping an `'unknown'` fallback means the feature degrades to "finding shown, severity unclear" rather than failing to show the finding at all.
- **Alternatives considered**: waiting to ship until a Copilot-reviewed pull request becomes available to probe the comment-body convention directly (rejected: this spec's own Phase 1 gate has already run once; blocking further on an external event — someone requesting a Copilot review on a real PR in this repo — has no fixed timeline, and the schema-absence finding above is sufficient to ship the `'unknown'` fallback now); inventing a severity from comment-body keyword matching as the primary source rather than a fallback (deferred: no live Copilot review sample exists yet to design a parser against; building one from documentation alone risks guessing a convention GitHub does not actually use).

### 5. Diff and pull-request truncation — **CONFIRMED, probe T002, 2026-10-04 (`docs/spike/FINDINGS.md` row 38)**

- **Decision**: `ChangedFile.patch` is `string | undefined` (the JSON key is absent, never `null`); a client reading the REST `pulls/{number}/files` response sees the `patch` key simply missing for a file over GitHub's size threshold, and that absence (not a `null` value, which never actually appears) drives the FR-011 banner ("too large to show in full") plus an "Open in browser" action that opens `https://github.com/<owner>/<repo>/pull/<number>/files` (or the file-specific anchor if one exists) via the existing external-link path. The same pattern covers "the whole pull request is too large" from the Edge Cases list: GitHub's whole-PR diff endpoint returns an explicit `406 … "code":"too_large"` error once a PR exceeds 3,000 changed lines or 300 changed files (confirmed live and current against `reviewdog/reviewdog#1696`), so the Overview must fetch per-file via `pulls/{number}/files` rather than relying on a single whole-diff call, and falls back to the fields it does have plus the same banner if that call itself errors.
- **Rationale**: this was confirmed two ways rather than guessed. (a) `gh pr view --json files` was confirmed live (PR #95, #96) to **never** include a `patch` key at all, even for a one-line diff — the porcelain CLI simply does not expose diff content, full stop; only `gh api repos/<owner>/<repo>/pulls/<n>/files` (REST) carries `patch`, confirmed live on the same two PRs. (b) GitHub's own Go client library source (`google/go-github`, `repos_commits.go`) tags the field `Patch *string \`json:"patch,omitempty"\``: `omitempty` means the JSON encoder drops the key entirely when the Go struct field is left unset for an over-threshold file, never emits `"patch": null`. No PR in the probed repo has a diff large enough to observe the per-file omission live (all 4 real PRs are one-line GitHub Actions version bumps), so this half rests on GitHub's own documented client-library contract rather than a live reproduction; the whole-PR 406 threshold (3,000 lines / 300 files) is independently confirmed live and current via a real, still-open public GitHub issue thread.
- **Alternatives considered**: calling `gh pr diff --name-only` plus a manual size check before fetching the full diff (rejected as redundant: the `--json` file objects already carry per-file additions/deletions, so a client-side cutoff would duplicate a signal GitHub already reports).

### 6. New session from a pull request: fork-safe branch checkout — **CONFIRMED, probe T005, 2026-10-04 (`docs/spike/FINDINGS.md` row 41)**

- **Decision**: "New session" fetches the pull request's head branch with `git fetch origin pull/<number>/head:<local-branch>` (this ref form works for both same-repository and fork pull requests, unlike assuming `headRefName` already exists as a local-fetchable branch name) and then runs `git worktree add <path> <local-branch>` — no `-b`, because the branch already exists after the fetch — reusing `src/main/git/worktrees.ts`'s existing failure-cleanup contract: any failed step removes whatever the attempt already created, so no half-created Session is ever left behind (FR-022, mirroring spec 001 T011's `addWorktree` guarantee).
- **Rationale**: a pull request's `headRefName` alone is ambiguous for a fork (the same branch name can exist locally for an unrelated purpose, or the fork's branch may never have been fetched at all); fetching the exact `pull/<number>/head` ref sidesteps both problems and is the same technique `gh pr checkout` itself uses, without requiring a `gh`-authenticated clone each time. T005's probe additionally found that GitHub keeps the `refs/pull/<n>/head` ref fetchable **indefinitely**, even after both the pull request and its source branch are closed/deleted — confirmed live by fetching a real closed PR (#97) whose head branch is independently verified gone from `git ls-remote --heads`, strengthening this rationale: `headRefName` alone would already have failed for that same PR, while `pull/<n>/head` still worked.
- **What T005 (`docs/spike/gh-pr-checkout-probe.mjs`) confirmed**: `git fetch origin pull/<number>/head:<local-branch>` then `git worktree add <path> <local-branch>` succeeds against the real `stuarthopwood/refract` remote for a same-repository pull request (#96). The exact "source ref is gone" error only occurs when fetching the bare (deleted) branch name directly, not via `pull/<n>/head`: `fatal: couldn't find remote ref <branch-name>`, **exit code 128** — the same error class/exit code was independently confirmed for a `pull/<n>/head` ref that never existed at all (a nonexistent PR number), giving the `checkout-failed` error code its exact, cited text and exit code. No cross-fork pull request exists on this repo today (all 4 real PRs are same-repository dependabot branches), so the cross-fork half of this decision is not independently reproduced this round; it remains based on `gh pr checkout`'s own documented use of the identical ref form for both same-repo and fork PRs, not on a live fork-PR fetch.
- **Alternatives considered**: `gh pr checkout <number>` directly (rejected: it operates against the *current* checkout, not an isolated worktree path, and would need to run inside the freshly created worktree after the fact in a way that risks a half-created Session if it fails partway — the existing `addWorktree`-style fetch-then-worktree-add sequence keeps the same atomic-cleanup shape every other Session-creation path already has).

### 7. UI placement: a left-nav "Pull requests" entry (Stuart's answer), and a shared cross-spec `view-store.ts`

- **Decision**: add a "Pull requests" entry at the top of the left nav (the session list column, above the repository groups), as Stuart answered, which opens a view with a repository dropdown and calls into `src/renderer/state/view-store.ts` to swap `App.tsx`'s main pane between `ChatPane` and the new `PullRequestsView`, scoped to that repository — see plan.md "Structure Decision" for the full rationale. `view-store.ts` is a single shared primitive, not a file this spec owns alone: coordinating live with the agents planning specs 004 and 008 (both of which also need to swap the main pane — Settings and Manage sessions respectively) produced one agreed shape so three specs don't each invent an incompatible `view-store.ts` and silently clobber each other's file:
  ```ts
  export type MainView = 'chat' | 'pull-requests' | 'settings' | 'manage-sessions'; // this spec adds 'pull-requests'; specs 004/008 add the other two
  interface ViewState {
    view: MainView;
    repositoryId: string | null; // relevant for 'chat' | 'pull-requests' (this spec's scoping)
    settingsSection: SettingsSectionId | null; // spec 004/008's field, unused by this spec
    openChat(repositoryId?: string): void;
    openPullRequests(repositoryId: string): void; // this spec's own action
    openSettings(section?: SettingsSectionId): void; // spec 004/008's action, untouched here
    openManageSessions(): void; // spec 008's action, untouched here
  }
  ```
  This feature only adds the `'pull-requests'` union member and the `openPullRequests` action; it does not implement `openSettings`/`openManageSessions`/`settingsSection`, which are specs 004/008's own scope.
- **Rationale**: Stuart's placement answer (spec 003 Clarifications) is a left-nav view with a "Pull requests" entry, so the plan follows it. The left nav today is the session list column; this spec adds only one entry at its top (not a new rail or shell), which specs 004, 007, and 008 can sit beside later. A single shared `view-store.ts` (rather than three parallel per-spec stores with incompatible field names) avoids whichever spec implements first silently fixing the shape for the others.
- **Alternatives considered**: waiting to implement this spec until a left nav exists (rejected: Stuart asked for every Draft spec's remaining Spec Kit steps now, and this feature's actual value — browsing and reviewing pull requests — does not depend on where its entry point sits); building a minimal placeholder left-nav rail just for this one entry (rejected: scope creep into specs 004/007/008's territory, and three different "first" left-nav implementations would need reconciling later instead of one); each spec keeping its own independent switch-state store (rejected: `App.tsx` can only render one main pane at a time, so a single source of truth is correct, and the cross-spec coordination above confirms the other two specs agree).

### 8. Markdown images: extend the existing sanitiser, don't build a second one

- **Decision**: pull request text (titles, bodies, comments, automated-reviewer output) renders through the existing `src/renderer/features/chat/Markdown.tsx` component unchanged in its sanitisation pipeline (`react-markdown` + `rehype-sanitize`); its `components` map gains one new entry, `img`, that renders the image's `alt` text as a link to the image's original `src` instead of loading it (FR-024).
- **Rationale**: the constitution (Principle V) and FR-023 already require every surface of untrusted text to go through "the app's sanitiser" — singular. A second markdown renderer for pull requests would be a second place that could drift out of sync with the chat's sanitisation rules.
- **Alternatives considered**: stripping `img` nodes entirely with no fallback (rejected: FR-024 explicitly requires the alt text plus a link, not silent removal).

### 9. Avatars: text/initials only, no image fetch in this spec

- **Decision**: every surface this spec adds (pull request rows, the Overview header's reviewers/assignees/author, timeline entries) shows a person as their display name or, where space is tight, initials — never an avatar image. This spec does not fetch, cache, or render any GitHub avatar.
- **Rationale**: FR-024 forbids loading avatar images into the app window at all; spec 008 ("the main process fetches the GitHub avatar, checks it is a small PNG or JPEG, caches it, and gives the window a local image") is the one spec that builds the fetch-and-cache machinery for avatars, for the profile item. Duplicating a second avatar pipeline here, before spec 008's is designed, would create two implementations of the same main-process image-fetch-and-validate logic.
- **Alternatives considered**: building a local avatar cache now and having spec 008 reuse it later (rejected: spec 008 is a separate, not-yet-planned feature; this plan does not get to design spec 008's data flow on its behalf).

### 10. Confirmations reuse the existing `AlertDialog` pattern

- **Decision**: `ReviewDialog.tsx` (approve / request changes) and `MergeDialog.tsx` (merge, with method picker) are built on the same shadcn `AlertDialog` component `src/renderer/features/sessions/DeleteDialog.tsx` already uses for a destructive confirmation, each naming the pull request and the exact action per FR-017.
- **Rationale**: reusing an existing, already-accessible confirmation pattern (keyboard-operable, visible focus, a named consequence) is both faster and more consistent than introducing a second confirmation primitive; `DeleteDialog.tsx` is the model spec 001 already established for "ask before an action with a real consequence."
- **Alternatives considered**: a plain `Dialog` with custom buttons (rejected: `AlertDialog` is the shadcn primitive specifically intended for "confirm a consequential action," and the project already has one working example to follow instead of inventing a second).

## Polling interval and rate-limit headroom — **CONFIRMED, probe T004, 2026-10-04 (`docs/spike/FINDINGS.md` row 40)**

- **Decision**: the renderer re-calls `pullRequests.detail` every 15 seconds while that pull request's check status is `pending` and its detail view is the one open, and stops polling once checks finish or the view closes; `pullRequests.list` is never polled (FR-006, FR-028).
- **Rationale**: `gh api rate_limit`, run live against the real account, reported `core: {limit: 5000, remaining: 5000}` and `graphql: {limit: 5000, remaining: 4999}` at probe time (a single prior GraphQL introspection call from this same session had used 1 point); a single open detail view polling every 15 s is `3600/15 = 240` requests/hour, confirmed to be `240/5000 = 4.8%` of the `core` budget, a small fraction as the decision assumed. The `rate-limited` error code's user-facing message is sourced from `gh`'s own open-source error formatting (`cli/go-gh` `pkg/api/errors.go`: `HTTPError.Error()` renders `"HTTP %d: %s (%s)"`, where the middle `%s` is GitHub's own JSON `message` field passed through verbatim) plus GitHub's published REST docs for the primary ("API rate limit exceeded for \<user-or-app\>.") and secondary ("You have exceeded a secondary rate limit. Please wait a few minutes before you try again.") rate-limit messages — not reproduced live, because deliberately provoking a 403/429 on a real, shared GitHub account risks burning real quota or tripping a secondary abuse limit with no safe undo (explicit user safety steer during the probe session). `gh`'s own command-error path has no special exit code for a rate-limited response; it falls through to the generic exit code 1 every `gh` command error uses.
- **Alternatives considered**: a fixed short interval with no cap (rejected: SC-004's "within 2 seconds" is about a *user's own action* reflecting quickly via a fresh fetch after that action, not about continuous fast polling, so a 15 s background interval already satisfies it without wasting rate-limit budget).
