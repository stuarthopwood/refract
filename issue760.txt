Feat: Chat: run custom commands and skills (/check-build, /skill:<name>): list and run the user's own commands by source, keep the allow-list for built-ins
> **Stuart 2026-10-13:** "Do we have an issue for running custom commands like `/check-build` or `skill:check-build`?" (No; filed on request.) OMP's own form for a skill is `/skill:<name>`.

## Problem (read on `origin/main` at `ae15586`, not run)
A user-authored command or skill **cannot be run from Refract**, by menu or by typing:
- `src/shared/slash-commands.ts` keeps a **hand-verified allow-list**, `SUPPORTED_OMP_COMMANDS` (about 22 built-ins probed on OMP 18.5.1, FR-032: "a command Refract has not verified MUST NOT be listed"). `filterSupportedCommands` drops everything else from the slash menu, and `chat.send` (`src/main/ipc/chat.ts`) refuses it with `unknown-command` (`classifySlashInvocation`), so typing `/check-build` by hand fails too.
- Even a **listed** command refuses arguments: any text after the bare name or one verified subcommand is `unsupported-arguments` ("refuse arguments entirely for now", `/add-dir` being the stated worry). A custom command that takes text cannot work under that rule.
- The descriptor type Refract keeps, `SlashCommandDescriptor` (`src/shared/frames.ts`), has **no `source` field**, so the app cannot tell a user's own command from a built-in.
The allow-list is right for **built-ins that can do damage** (`/session delete`, `/todo copy`, `/usage reset`, #129). It is the wrong tool for **commands the user wrote**, which no probe can enumerate.

## What OMP provides (from the installed OMP docs, to be confirmed by a probe on 18.10.1)
- **Discovery over RPC:** `get_available_commands` returns `{ commands }` and the same array is pushed in `available_commands_update`; each command has `name`, `source`, optional `aliases`, `description`, `input.hint` and `subcommands`. OMP's catalog covers "builtins/custom/MCP/file commands" with a "broader `source` enum" (`omp://rpc.md`).
- **Where custom commands come from** (`omp://slash-command-internals.md`): project `<cwd>/.omp/commands/*.md`, user `~/.omp/agent/commands/*.md` (or the named profile's), Claude `.claude/commands/**` (a `foo/bar.md` is also registered as `foo:bar`), Codex and OpenCode command folders, `.agent(s)/commands`, plugins (`<plugin>:<command>`) and TypeScript custom commands. Same name: first provider wins and the loser is marked shadowed; `disabledExtensions` can omit individual commands.
- **Skills:** `/skill:<name> [args]` and the namespaced `/skill:<namespace>/<name>`, registered **when `skills.enableSkillCommands` is true** (`omp://skills.md`). `prompt` accepts a `/skill:` invocation over RPC (`omp://rpc.md`: image acknowledgement note "applies to a `/skill:` invocation sent through `prompt`"; queued skill commands keep their original `/skill:<name>` as the chip text). Whether the **RPC command list includes the skill commands**, and under which setting, is not documented: probe.
- **Running:** a custom or extension command that starts no turn completes locally (`agentInvoked: false`) and may emit `command_output` frames; a file command expands to a prompt and runs a normal turn. OMP **rewrites** the submitted text (custom-command rewriting, prompt-template expansion), so the transcript's user message may hold the **expansion**, while the queue chip holds the **original** `/check-build`.
- Refract already handles `command_output` (`SessionAgent.ts` line 1525, `transcript.ts` line 795) as a notice row; that is the existing path for a local-only command.

## Proposal (mine, for Stuart to change)
**1. Policy: allow-list for built-ins, source-based for the user's own.** Keep `SUPPORTED_OMP_COMMANDS` **only** for commands whose `source` is built-in. A command whose `source` is a custom, file, plugin or skill source is **listed and runnable**, with **free-form arguments**. Trust OMP's `source`, never the name (a custom command named `session` must not inherit a built-in's rules or bypass its denylist). Keep `NATIVE_RESERVED_COMMANDS` (`new`, `resume`, `plan`, `fork`, `settings`, `pause`, `plan-review`, `btw`) refused locally even if a custom command takes the name (constitution I). An unknown name is still `unknown-command`. Add `source` to `SlashCommandDescriptor` (and #519, which would generate these types from OMP's wire schema, removes the hand-typing risk).
**2. The slash menu** (`SlashMenu.tsx`): sections **Commands** (built-in), **Custom** (project, user, plugin, with the source named in text: "project", "user", "plugin <name>", never colour alone) and **Skills**. Show `description` and the `input.hint` after the name. Selecting a command that takes input inserts `/name ` and leaves the cursor for arguments; Enter sends. **Skills are numerous** (a user can have well over a hundred), so they appear only when the typed text matches (`/skill:` or a substring), as a windowed, filtered list, never flooding the default menu. Typing a complete valid command with the menu closed works too.
**3. Sending and display:** the user bubble shows **what the user typed** (`/check-build main`), with the expansion available collapsed, not the expanded prompt body; this is the same treatment #547 gives a user-invoked skill ("Skill invoked: <name>", body collapsed): do #547 first or together. The queue chip text stays the original. A command's `command_output` renders as the existing notice row.
**4. Settings:** a switch for `skills.enableSkillCommands` in the Agents (OMP) group of #714, through #691 (read and write OMP config keys), if the probe shows RPC lists skill commands only when it is on. Without it, skills run only if typed.
**5. Safety and trust:** nothing runs on its own; the user picks or types it, and the resulting turn runs under the Session's approval mode like any other prompt. A **project** command comes from the repository, so the menu labels it "project" and its tooltip names the file (`<repo>/.omp/commands/check-build.md`); no extra confirmation unless the probe finds a command form that executes something outside the approval model.
**6. Spec:** this amends spec 001 FR-032 and FR-033 ("MUST NOT be listed" becomes "built-ins only; user-authored commands are listed by source") through Spec Kit and the constitution's IV check (probe before design).

## Not in scope
Creating or editing command and skill files from Refract (the Agent Builder panel is a separate idea), a command palette (#5, closed), the per-command argument forms of the built-ins (they stay as verified), MCP prompt commands unless the probe shows they arrive with the same shape.

## Accessibility (WCAG 2.1 AA)
The menu is the existing combobox-style slash menu: grouped options with text section headings, the source named in text, keyboard filtering and arrows, an announced result count ("12 commands"); the argument hint is read as part of the option; a refused command (reserved or unknown) is announced through the existing error path; nothing depends on colour.

## Acceptance
- Probe results recorded on this issue.
- With a user command `check-build` and a project command, typing `/ch` lists them under **Custom** with their source; `/check-build main` runs, the bubble shows exactly what was typed, the turn or the `command_output` appears, and the queue chip (if queued) shows the original text.
- `/skill:<name>` runs a skill and shows as "Skill invoked: <name>" with the body collapsed (#547).
- Built-ins keep today's rules: `/session delete`, `/todo copy` and the other unverified subcommands are still refused; `/new`, `/plan` and the other reserved names are refused even if a custom command has that name; an unknown name is still `unknown-command`.
- A command that shadows a built-in's name follows the probe's finding and does not bypass the denylist.
- Typecheck, unit tests for the policy (source built-in vs custom vs skill, reserved names, shadowing, arguments), a menu test for grouping and skill filtering, and a live check on a scratch instance with a real command file.
